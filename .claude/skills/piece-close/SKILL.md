# /piece-close — 조각 마무리 (5~7단계)

## 5. 검증 증거
- "됐다"고 말하지 않는다. **증거를 붙인다**: 테스트 실행 출력(통과/실패 수), 실제 기동 로그, `curl` 요청과 응답, DB 조회 결과, 훅/ArchUnit 출력.
- 검증 중 막혔던 것은 `/trouble`로 기록하고 여기서 링크한다.
- 증거가 없는 주장은 "확인 못 함"이라고 명시한다.

## 6. 코드 워크스루 — 요청이 들어와서 나가는 순서대로
파일 순서가 아니라 **실행 순서**로 따라간다.
1. 진입점: HTTP 요청(메서드·경로·바디) 또는 이벤트/훅 입력.
2. 필터·인터셉터·인자 리졸버 → 컨트롤러 → 서비스(트랜잭션 시작 지점 표시) → 리포지토리/외부 호출 → 커밋 → 이벤트 → 응답.
3. 각 단계에서 바뀐 줄을 `파일:줄`로 짚고, **"이 줄을 빼면 무엇이 깨지는가"**를 구체적인 실패 시나리오로 말한다(어떤 입력 → 어떤 잘못된 결과·예외).
4. commerce-msa에서 같은 역할을 했던 코드가 있으면 비교한다.
5. 공개 설계서의 `워크스루 요약`에 3~6줄로 압축해 남긴다.

## 7. 이해 게이트
- 질문은 **본 작업 2~3개, 하네스 조각 1개**.
- 암기형("어노테이션 이름은?")이 아니라 **"왜"와 "만약 ~라면"**. 이번 조각의 핵심 트레이드오프를 건드려야 한다.
  - 좋은 예: "만약 이 검증을 락을 잡기 전에 하면 어떤 요청 순서에서 무엇이 깨지나?"
- `docs/private/gates.md`에 이번 조각 섹션을 만들고 질문을 적는다(답 칸은 비움).
- `docs/private/roadmap.md` 상태 블록을 `단계: 7/8 (이해 게이트)`, `직전 게이트: OPEN`으로 바꾸는 편집을 한다(승인 필요).

## 멈춘다
질문을 던지고 끝낸다. 사용자의 답을 받으면 `/gate-review`로 넘어간다.
