# ADR-0003: 모놀리식 앞에 Spring Cloud Gateway를 세우고, 서비스마다 독립 Gradle 프로젝트로 둔다

- **상태**: 채택
- **날짜**: 2026-10-14
- **로드맵 단계**: 3
- **관련 설계서**: [design/3-strangler-facade.md](../design/3-strangler-facade.md)

## 맥락

[ADR-0001](0001-bounded-contexts-and-extraction-order.md)에서 Place Catalog를 처음 떼어내기로 했고, [ADR-0002](0002-public-api-package-per-module.md)로 컨텍스트 사이의 직접 사용을 274건에서 0건으로 끊었다. 코드는 떼어낼 수 있는 모양이 됐지만, 떼어낸 뒤의 요청이 어디로 갈지가 정해져 있지 않았다.

- 클라이언트는 모놀리식 주소(`:8080`) 하나만 안다. Catalog를 떼면 `/api/v1/places/**`의 일부가 다른 프로세스로 가야 하는데, 앞단 입구가 없으면 클라이언트가 주소 두 개를 알아야 한다. 외부 계약이 바뀐다.
- 레포 루트 전체가 모놀리식이었다. 여기에 Gateway를 추가하면 `src/` 옆에 하위 프로젝트가 붙어서, 떼어낸 서비스가 모놀리식의 부속처럼 보인다.
- 루트에는 팀이 EC2에 배포하던 자산이 섞여 있었다. `docker-compose-blue.yml`은 팀의 ghcr 이미지와 외부 네트워크 `bready_default`를 썼다. 이 레포에서는 실행할 수도, 실행해서도 안 되는 파일이었다.
- 앱을 확인하려면 MySQL·Redis 컨테이너, 모놀리식 `bootRun`, Gateway `bootRun`을 손으로 하나씩 띄워야 했다. 루트 빌드를 없앤 뒤로는 원격에서 서비스별 빌드를 확인하는 장치도 없었다.

증명할 것은 하나였다. **Gateway를 끼우기 전과 후의 응답이 같다.**

## 선택지

**1. Gateway 구현**

| | Spring Cloud Gateway | nginx | 별도 Gateway 없이 모놀리식이 넘겨 줌 |
|---|---|---|---|
| 방법 | Spring 애플리케이션으로 라우트를 yml에 둔다 | 설정 파일로 리버스 프록시 | 떼어낸 경로를 모놀리식이 받아 새 서비스로 다시 보냄 |
| 얻는 것 | 라우팅을 JUnit으로 고정할 수 있다. 서킷브레이커·JWT 필터를 Java로 같은 자리에 붙인다 | 가볍고 빠르다. 지금 하는 일(전부 8080으로)은 몇 줄이면 된다 | 새 프로세스가 없다 |
| 잃는 것 | JVM 프로세스 하나가 더 뜬다 | 요청마다 판단하는 로직(서킷브레이커, 토큰 검증)을 붙이기 어렵고 자동 테스트가 어렵다 | 모놀리식을 없앨 수 없게 된다. Strangler의 목적과 반대다 |
| 되돌리기 비용 | 중간 | 중간 | 높다 |

**2. 레포 구조**

| | 루트가 모놀리식 + `include` | 루트 `settings.gradle`로 묶은 멀티 모듈 | 서비스마다 독립 Gradle 프로젝트 |
|---|---|---|---|
| 얻는 것 | 파일을 옮기지 않는다 | 한 명령으로 전체 빌드, 공통 모듈을 쉽게 만든다 | 서로의 코드를 가져다 쓸 방법이 아예 없다. 구조가 독립을 드러낸다 |
| 잃는 것 | 구조가 비대칭이다 | 공통 모듈로 서비스가 다시 코드로 묶이기 쉽다 | 전체 빌드가 한 명령이 아니다. 빌드 설정이 서비스마다 중복된다 |
| 되돌리기 비용 | 낮다 | 중간 | 중간(304개 파일 이동) |

**3. 인증과 CORS**

| | 모놀리식에 그대로 | Gateway | 양쪽에 두고 중복 헤더 제거 |
|---|---|---|---|
| JWT | 6단계 전에는 건드리지 않는다 | 6단계의 일 | — |
| CORS | 처음 결정. Gateway는 통과만 | preflight를 Gateway가 판정, 모놀리식은 끈다 | 허용 Origin을 두 곳에서 똑같이 유지해야 한다 |

**4. 로컬 실행**

| | 인프라만 compose | `app` 프로필로 앱까지 | 전부 기본으로 |
|---|---|---|---|
| 얻는 것 | 변경 없음 | `up`이면 인프라만(IDE 디버깅), `--profile app up`이면 전체 | 명령이 가장 단순 |
| 잃는 것 | 손으로 띄우는 절차가 서비스 수만큼 는다 | Dockerfile 2개, 프로필 개념 | IDE로 띄운 앱과 포트가 충돌한다 |

**5. 옛 팀 배포 자산**

| | 삭제 | `legacy/`로 이동 | 그대로 |
|---|---|---|---|
| 얻는 것 | 루트가 서비스와 로컬 구성만 남는다. "만지지 마" 규칙과 훅이 필요 없다 | 파일이 눈에 보인다 | 변경 없음 |
| 잃는 것 | 작업 트리에서 사라진다(git 히스토리와 원본 레포에는 남는다) | 실행할 수 없는 파일을 계속 지켜야 한다 | 레포가 무엇을 하는지 헷갈린다 |

## 결정

**1. Spring Cloud Gateway.** 결정적인 이유는 "끼워도 응답이 같다"를 자동 테스트로 고정할 수 있다는 것과, 5단계 서킷브레이커·6단계 토큰 검증이 붙을 자리가 Java 필터라는 것이다. 지금은 라우트 하나(`Path=/** → ${MONOLITH_URI:http://localhost:8080}`)뿐이고, 4단계부터 좁은 라우트를 그 위에 끼운다. 의존성은 gateway·actuator만 둔다.

**2. 서비스마다 독립 Gradle 프로젝트(`monolith/`, `gateway-service/`), 루트에는 빌드가 없다.** 서비스 사이에서 지켜야 하는 것은 같은 클래스가 아니라 같은 HTTP 계약이고, 그것을 구조로 강제한다. 공통 코드가 필요해지면 4단계에서 실제로 필요한 만큼만 정한다.

**3. JWT는 모놀리식, CORS는 Gateway.** 처음에는 둘 다 모놀리식에 두기로 했다. 실제 기동 비교에서 모놀리식이 허용하는 Origin의 preflight가 `:8080`은 200, `:8000`은 403이었다. Gateway(WebFlux)의 핸들러 매핑은 preflight를 라우트로 넘기지 않고 그 자리에서 판정한다. 모놀리식에 두는 설계는 Gateway 뒤에서 성립하지 않았다([T-009](../TROUBLESHOOTING.md#t-009)). CORS는 Gateway의 `globalcors` 한 곳에서만 붙이고, 모놀리식은 `.cors(cors -> cors.disable())`로 끈다. 두 곳에서 붙이면 `Access-Control-Allow-Origin`이 두 번 나가 브라우저가 거부한다.

**X-Forwarded 헤더는 켜지 않는다.** Gateway 4.3은 `trusted-proxies`를 설정해야 이 헤더를 붙인다([T-008](../TROUBLESHOOTING.md#t-008)). 모놀리식에 Host로 URL을 만들거나 클라이언트 IP를 쓰는 코드가 0건이다.

**4. `app` 프로필.** `docker compose --profile app up --build`로 Gateway와 모놀리식이 함께 뜬다. 모놀리식은 호스트에 포트를 열지 않는다. 클라이언트가 들어올 수 있는 곳은 Gateway(8000)뿐이고, CORS를 Gateway로 옮긴 전제가 구조로 지켜진다. Dockerfile은 멀티 스테이지로 이미지 안에서 빌드한다. 호스트에서 jar를 빠뜨려 옛 코드가 뜨는 일이 없다.

**5. 삭제.** `deploy/`, `nginx/`, `docker-compose-{blue,green,prod,infra}.yml`, `application-cd.yml`을 지운다. 보존은 git 히스토리와 원본 레포가 이미 한다. 코드 리뷰 봇 설정(`.coderabbit.yaml`)은 배포 자산이 아니라 지금 쓰는 도구라 남기고, 서비스 디렉터리 구조와 규칙 파일(`.claude/rules/`)에 맞게 고친다.

**CI도 함께 둔다.** 루트 빌드가 없어서 원격 검증이 서비스마다 필요해졌다. GitHub Actions가 `gradlew`가 있는 최상위 디렉터리를 찾아 서비스마다 `./gradlew build`를 돌린다. 서비스 목록을 손으로 적지 않는 이유는, 4단계에서 서비스를 추가하고 목록을 빠뜨리면 그 서비스가 조용히 검사에서 빠지기 때문이다. 로컬 검증 스크립트와 Stop 훅도 같은 규칙으로 서비스를 찾는다. 외부 키 없이 테스트가 돌기 때문에 시크릿을 하나도 쓰지 않는다.

## 결과

- 좋아지는 것:
  - 클라이언트가 아는 주소가 `:8000` 하나로 고정됐다. 4단계부터는 라우트만 바꾼다.
  - 같은 요청 12종을 Gateway를 끼우기 전과 후로 비교해 상태 코드가 모두 같았다. 본문·헤더까지 같은 것은 9종이고, 나머지는 CORS 거절 응답의 본문과 `Vary` 헤더 차이다. 그리고 그 비교로 preflight 문제를 찾았다.
  - 라우팅·CORS·전달 헤더를 Gateway 테스트 8개가 고정한다. 누가 `trusted-proxies`를 켜거나 뒤쪽 서비스가 CORS를 다시 붙이면 테스트가 깨진다.
  - 한 줄로 전체를 띄우고, 컨테이너 사이에서 `MONOLITH_URI`가 처음으로 실제 다른 값(`http://monolith:8080`)으로 쓰였다.
  - 루트에 실행할 수 없는 파일이 없다. 서비스가 늘어도 CI·검증 스크립트·훅은 고칠 곳이 없다.
- 감수하는 것 (트레이드오프):
  - 모놀리식이 죽으면 Gateway가 Spring 기본 형식의 500을 낸다. 의미상 503이고 `CommonResponse` 형식도 아니다.
  - 브라우저가 `:8080`을 직접 부르면 CORS 헤더가 없다. 개발 중 모놀리식만 띄워 프론트를 붙이면 안 된다.
  - 모놀리식은 모든 요청을 Gateway에서 온 것으로 본다. 클라이언트 IP를 모른다.
  - OAuth `redirect-uri` 기본값이 `:8080`이라 콜백은 Gateway를 거치지 않는다.
  - 첫 이미지 빌드가 느리다(의존성 다운로드, 약 1분 20초). 빌드 설정이 서비스마다 중복된다.
  - 블루/그린 배포 방식은 이 레포에서 사라졌다. 다시 배포가 필요해지면 새로 설계한다.
- 나중에 다시 볼 조건 (이 결정을 뒤집을 신호):
  - 5단계에서 장애 전파를 재현할 때 Gateway에 타임아웃·서킷브레이커를 붙인다. 그때 500을 503 + `CommonResponse`로 바꾼다.
  - 모놀리식이나 떼어낸 서비스가 클라이언트 IP를 써야 하면(IP별 시도 제한 등) `trusted-proxies`를 실제 프록시 주소로만 켜거나, 그 제한을 Gateway에서 한다.
  - 6단계에서 인증을 떼어낼 때 토큰 검증을 Gateway로 옮길지 정한다. OAuth 콜백 주소도 그때 Gateway로 바꾼다.
  - 4단계에서 응답 봉투·에러 형식을 서비스마다 다시 만드는 비용이 커지면, 공통 라이브러리를 둘지 HTTP 계약만 맞출지 다시 정한다.
  - 서비스가 늘어 CI 시간이 길어지면 바뀐 서비스만 빌드하도록 경로 필터를 단다.
