# ADR-0001: 바운디드 컨텍스트를 여섯으로 확정하고 가장자리부터 떼어낸다

- **상태**: 채택
- **날짜**: 2026-10-12
- **로드맵 단계**: 1
- **관련 설계서**: [design/1-boundary-map.md]

## 맥락

모놀리식 BReady는 패키지가 9개(`auth` `user` `plan` `place` `trigger` `recommendation` `stats` `s3` `global`)다. 패키지를 그대로 서비스 경계로 삼을 수 있는지 조사한 결과([경계 지도](../architecture/context-map.md)) 그럴 수 없다는 근거가 나왔다.

- `category_states`의 한 행을 `plan`, `place`, `trigger` 세 패키지의 서비스가 비관적 락으로 잠그고 수정한다. 후보 등록, 대표 지정, 전환, 카테고리 타입 변경이 모두 그렇다.
- 전환(`SwitchService.executeSwitch`)은 한 트랜잭션에서 `decisions` 조회, `place_candidates` 검증, `category_states` 락과 변경, `switch_logs` 기록을 한다.
- `place` 패키지 안에 성격이 다른 두 개념이 섞여 있다. `Place`는 카카오에서 가져온 공용 장소 데이터이고, `PlaceCandidate`는 특정 플랜 카테고리에 올려 둔 후보다. 카테고리 타입을 바꾸면 후보가 전부 지워진다.
- ArchUnit 기준선은 패키지를 모듈로 보고 경계 위반을 435건으로 센다. 경계를 어디에 긋느냐에 따라 이 중 무엇을 끊어야 하는지가 달라진다.

또 어느 것부터 떼어낼지에 따라 모듈러 모놀리스 단계에서 먼저 열어야 할 공개 API가 달라지므로, 경계와 순서를 함께 정한다.

## 선택지

### 1. trigger를 어디에 둘까

| | A. Planning에 합친다 | B. 별도 컨텍스트 |
|---|---|---|
| 방법 | plan + 후보 + trigger를 한 컨텍스트로 | trigger를 독립 서비스 후보로 |
| 얻는 것 | 전환이 한 트랜잭션, 한 락으로 유지된다. trigger → plan·place 참조 38건을 끊지 않아도 된다 | 컨텍스트가 작아진다 |
| 잃는 것 | Planning이 테이블 8개로 커진다 | 전환이 두 서비스에 걸친다. DB 락이 서비스 경계를 넘지 못해 동시성 보장을 다시 설계해야 하고, 대표 변경과 이력 기록이 따로 커밋되어 보상이 필요하다 |
| 되돌리기 비용 | 나중에 떼기는 어렵다 | 합치기는 비교적 쉽다 |

### 2. 장소 후보를 어디에 둘까

| | A. 후보는 Planning, 장소만 Place Catalog | B. 지금처럼 place에 함께 |
|---|---|---|
| 얻는 것 | 후보의 생명주기가 카테고리에 묶여 있다는 사실과 경계가 일치한다. plan ⇄ place 순환이 사라진다 | 코드 이동이 없다 |
| 잃는 것 | 패키지 이동이 필요하다 | Place Catalog를 떼어낼 때 후보가 딸려 가거나 그때 갈라야 한다 |

### 3. auth와 user

| | A. 하나의 Identity | B. 둘로 나눈다 |
|---|---|---|
| 얻는 것 | 가입이 `users` 쓰기와 토큰 발급을 한 번에 한다는 사실과 일치한다. auth → user 참조 67건이 내부 참조가 된다 | 인증 서버를 독립시킬 수 있다 |
| 잃는 것 | 인증만 따로 확장하기 어렵다 | 가입·로그인마다 서비스 간 호출이 생긴다 |

### 4. 추출 순서

| | A. Place Catalog → Recommendation → Stats | B. Recommendation부터 | C. Stats부터 |
|---|---|---|---|
| 얻는 것 | 첫 추출에서 호출이 한 방향뿐이다. 테이블 이관과 FK 끊기를 처음부터 겪는다 | 테이블이 없어 추출 자체는 가장 쉽다 | 이미 이벤트 기반이다 |
| 잃는 것 | 첫 추출부터 "장소 정보를 복사할지, 조회할 때 부를지"를 정해야 한다 | 모놀리식에 조회용 내부 API를 먼저 열어야 한다. 데이터 이관이 뒤로 밀린다 | 첫 추출부터 메시지 브로커와 유실 방지가 필요하다 |

## 결정

1. **바운디드 컨텍스트는 여섯이다.** Identity(auth + user), Planning(plan + 장소 후보 + trigger), Place Catalog(장소 검색 + `places`), Recommendation, Stats, File(s3).
2. **Planning은 쪼개지 않는다.** 한 트랜잭션과 한 락으로 함께 바뀌는 것은 같은 경계에 둔다.
3. **추출 순서는 Place Catalog → Recommendation → Stats다.** Planning과 Identity는 모놀리식에 남긴다.

결정적인 이유는 둘이다.

- 서비스를 나누면 DB가 나뉘고, DB가 나뉘면 트랜잭션과 락이 그 선을 넘지 못한다. 전환, 후보 등록, 카테고리 타입 변경은 지금 그 둘에 기대어 정합성을 지킨다. 이것을 서비스 간 보상으로 바꾸는 비용에 비해 trigger를 따로 배포해서 얻는 것이 없다.
- Place Catalog는 나가는 의존이 없다. 떼어낸 서비스가 모놀리식을 부르지 않으므로 장애가 한 방향으로만 퍼지고, 서로 호출하는 구조가 될 위험이 없다. 첫 추출로 가장 안전하다.

함께 정한 것:

- 인가 누락(트리거·결정·전환·후보 API가 소유자를 확인하지 않음)은 모듈러 모놀리스 단계에서 Planning의 진입점을 정리할 때 고친다. trigger와 후보가 Planning 안에 있으므로 같은 컨텍스트 안의 검증이 된다.
- 소프트 삭제 불일치(삭제한 플랜의 트리거가 통계에 섞임)는 버그로 기록하고, Stats를 떼면서 읽기 모델을 새로 만들 때 고친다. 그 쿼리들은 그때 전부 다시 쓴다.

## 결과

- 좋아지는 것:
  - 기준선 435건 중 약 189건(43%)은 같은 컨텍스트 안의 참조가 되어 끊지 않아도 된다. 끊을 대상은 약 246건이고 대부분 stats와 recommendation에서 나온다.
  - plan ⇄ place 순환과 trigger → plan 연관은 "끊을 것"이 아니라 "한 컨텍스트로 모을 것"이 된다.
  - 모듈러 모놀리스 단계에서 먼저 만들 공개 API가 정해진다. Planning이 Place Catalog에 묻는 것부터다.
- 감수하는 것 (트레이드오프):
  - Planning이 테이블 8개를 가진 큰 컨텍스트가 된다. 플랜, 후보, 트리거 기능을 따로 배포하거나 따로 늘릴 수 없다.
  - 통계의 소프트 삭제 버그가 Stats 추출 때까지 남는다.
  - 첫 추출에서 플랜 상세 조회가 장소 정보를 어떻게 가져올지를 결정해야 한다.
- 나중에 다시 볼 조건 (이 결정을 뒤집을 신호):
  - trigger 쪽에 대표 후보 상태(`category_states`)를 건드리지 않는 기능이 늘어난다. 예: 트리거 자동 감지, 알림, 외부 날씨 연동. 이런 변경이 잦아져 Planning 전체를 매번 배포하게 되면 trigger를 떼는 것을 다시 검토한다.
  - trigger의 부하나 장애 특성이 플랜·후보와 뚜렷이 달라진다.
  - 반대로 대표를 바꾸는 기능이 늘어나는 것은 합쳐 둘 이유가 강해지는 것이므로 신호가 아니다.
  - Identity는 인증 방식을 바꾸는 단계에서 다시 본다.
