# /refactor-legacy — 옛 코드 정리

**리팩터링 = 동작은 그대로, 구조만 바꾼다.** 동작을 바꾸는 수정(버그 수정, 계약 변경)과 섞지 않는다.

먼저 읽는다: `rules/00-map.md`의 "옛 코드와 새 규칙", 정리할 계층의 규칙 파일, `rules/testing.md`.

## 1. 범위를 정한다 (사용자에게 보여준다)
```
대상: PlanService (plan/service/PlanService.java)
위반: 소유권 검증 복붙 4회(entity 4번) · 응답 빌더 조립(dto 4번) · 클래스 트랜잭션 선언 없음(service-transaction 2번)
범위 밖: PlanService가 UserRepository를 쓰는 경계 위반(V1) → 2단계 조각에서
동작 변경: 없음
```
- 한 번에 한 클래스, 또는 한 가지 규칙. 여러 모듈을 동시에 정리하지 않는다.
- 경계 위반(V1~V6) 끊기는 2단계 조각의 일이다(`msa-boundary.md` 5번). 여기서 하지 않는다.
- 계약(URL·JSON 필드·에러 코드)이 바뀌는 변경은 리팩터링이 아니다 → 별도 조각 + ADR.

## 2. 안전망 확인
- 이 코드의 동작을 지키는 테스트가 있는가? 어느 계층인가?
- 없거나 엔티티 mock 때문에 믿기 어렵다면, **먼저 현재 동작을 고정하는 테스트**를 쓴다(`/write-test` 5번의 characterization test).
  - 현재 동작이 버그여도 일단 그대로 고정하고, 테스트 이름에 버그라고 적는다. 고치는 건 별도 커밋.
- 안전망 테스트가 통과하는 것을 확인하고 출력을 남긴다. **이 출력이 리팩터링 전 기준선이다.**

## 3. 작은 단위로 바꾼다
한 단계마다 테스트를 돌린다. 순서 예:
1. 죽은 코드·쓰지 않는 import 제거
2. 이름 정리(지역 변수 → 메서드 → 클래스)
3. 중복을 원래 있어야 할 곳으로 이동(엔티티 메서드, enum, private 헬퍼)
4. 변환을 DTO `from()`으로 이동
5. 트랜잭션 선언 정리
6. 예외 생성 통일(`ApplicationException.from`)

단계 중간에 테스트가 깨지면 그 단계만 되돌리고 원인을 본다. 테스트를 고쳐서 통과시키지 않는다(테스트가 틀렸다는 근거가 있을 때만, 사용자에게 알리고).

## 4. 같은 동작임을 증명한다
- 2단계 기준선과 같은 테스트가 모두 통과하는 출력을 붙인다.
- 정리 전후의 핵심 코드를 짧게 비교해 보여준다(줄 수, 메서드 수, 복붙 제거 수).
- 정리하면서 발견한 버그·경계 위반은 고치지 말고 목록으로 남긴다(다음 조각 후보).

## 5. 커밋 나누기 (`/git-handoff`)
- 안전망 테스트 추가 → 리팩터링(단계별 또는 묶어서) → (있다면) 버그 수정, 순서로 커밋을 나눈다.
- 포맷만 바뀐 커밋은 단독으로.

## 체크리스트
- [ ] 리팩터링 전 안전망 테스트 통과 출력이 있다
- [ ] 동작 변경·계약 변경·경계 끊기가 섞이지 않았다
- [ ] 매 단계 테스트를 돌렸다
- [ ] 발견한 버그·위반을 목록으로 남겼다
- [ ] 고친 코드가 `.claude/rules/`의 "BReady 현황" 근거였다면 그 항목을 지우거나 줄 번호를 갱신했다
