## 2026-10-08 · 출발점: 경계 지도 초안

**문제**

모놀리식을 서비스로 쪼개려면 먼저 어디가 엉켜 있는지 알아야 한다. 모르고 시작하면 첫 추출부터 "한 트랜잭션으로 묶여 있던 것이 두 서비스로 갈라지는" 문제를 만나고, 그때 가서야 분산 트랜잭션을 고민하게 된다.

**한 것**

코드를 한 줄도 고치지 않고 전체를 조사해서 [경계 지도](architecture/context-map.md)를 그렸다. 본 것은 네 가지다. 모듈 사이의 import 방향, 모듈을 넘는 JPA 연관, 다른 모듈 테이블을 JOIN하는 쿼리, 한 트랜잭션에서 여러 모듈의 데이터를 쓰는 곳.

**배운 것**

- 패키지와 바운디드 컨텍스트는 같지 않다. `plan`, `place`의 후보, `trigger`는 패키지는 셋이지만 `category_states`의 한 행을 비관적 락으로 함께 수정한다. 같은 락과 같은 트랜잭션으로 묶여 있으면 하나의 덩어리로 봐야 한다.
- 모듈 사이의 결합은 대부분 "남의 서비스를 부르는 것"이 아니라 "남의 리포지토리를 직접 주입받는 것"이었다. 서비스 호출은 나중에 HTTP 호출로 바꿀 수 있지만, 리포지토리 주입은 남의 DB에 직접 붙는 것이라 서비스를 나누는 순간 불가능해진다.
- 모든 패키지를 서비스로 만드는 것이 목표가 아니다. 어디를 쪼개지 않을지 근거를 대는 것이 더 중요하다. 그래서 플래닝 코어는 하나로 두고 가장자리부터 떼기로 방향을 잡았다.

## 2026-10-12 · 0-1 키 없이 로컬 기동

**문제**

레포를 클론한 그대로는 앱이 뜨지 않았다. 원인은 설정이 운영 서버에만 있다는 것이었다.

- 기본 설정 파일 `application.yml`이 `.gitignore`에 걸려 레포에 없었다. 실제 키가 들어 있어서 팀이 무시해 둔 파일이다.
- 그 결과 앱 전체를 띄우는 테스트 `contextLoads`가 실패했다. 나머지 99개는 스프링을 띄우지 않는 단위 테스트라 통과했고, 그래서 문제가 눈에 띄지 않았다.

앱이 안 뜨면 통합 테스트를 한 줄도 쓸 수 없다. 안전망을 만들기 전에 이것부터 풀어야 했다.

**선택지와 결정**

| 안 | 방법 | 버린 이유 또는 고른 이유 |
|---|---|---|
| A | 키 없는 `application.yml`을 커밋하고 모든 외부 값을 `${환경변수:로컬더미값}`으로 둔다 | 채택. 프로덕션 코드를 건드리지 않고 클론 직후 뜬다 |
| B | 외부 연동 빈을 프로파일로 끄거나 가짜 구현으로 바꾼다 | 프로덕션 코드에 조건 분기와 가짜 클래스가 생긴다. 아직 외부 호출을 흉내 내야 할 일이 없었다 |
| C | 테스트 설정에만 더미 값을 넣는다 | 테스트는 통과해도 로컬 기동은 여전히 안 된다 |

실제 키가 필요할 때를 위해 `application-local.yml`을 따로 두고 `.gitignore`에 넣었다. `local` 프로파일을 켤 때만 읽힌다. 처음에는 실제 키 파일 이름을 `application.yml`로 그대로 두려고 했는데, 그러면 테스트도 그 파일을 읽는다. 메인 리소스는 테스트 클래스패스에도 올라가기 때문이다. 프로파일 파일로 분리해야 기본 실행과 테스트가 실제 키를 보지 않는다.

A의 대가는 분명하다. 더미 키로는 빈만 만들어질 뿐이고 카카오 검색이나 S3 업로드를 실제로 부르면 그 시점에 실패한다.

**배운 것**

1. 설정 값은 호출할 때가 아니라 빈을 만들 때 해석된다. `S3Config`가 `@Value("${cloud.aws.credentials.access-key}")`를 주입받는 순간 값이 없으면 기동 자체가 멈춘다. S3를 한 번도 쓰지 않는 테스트가 S3 설정 때문에 실패한 이유다. 불편해 보이지만, 요청이 들어온 뒤에 터지는 것보다 뜰 때 터지는 편이 낫다.

2. 막힌 곳은 한 겹이 아니었다. S3 값을 채우니 그 뒤에 `OpenAI API key must be set`이 나왔다. 더미 환경변수를 한 겹씩 채워 가며 돌려서 두 겹이 전부라는 것을 확인했다.

3. 우리 스위치는 우리 빈만 끈다. `recommendation.ai.enabled=false`로 AI 추천을 꺼 두었는데도 OpenAI 키를 요구했다. 그 스위치는 우리가 `@ConditionalOnProperty`를 붙인 빈 4개만 끄고, 키를 요구한 `openAiAudioSpeechModel`은 Spring AI 라이브러리가 자동으로 만드는 빈이었다. 자동 설정을 exclude하는 방법도 있었지만, 그러면 AI를 켰을 때 우리 `ChatClient` 빈이 필요로 하는 `ChatModel`이 없어서 기동이 실패한다. 스위치와 exclude 두 군데를 맞춰야 하는 구조가 되므로 더미 키 쪽을 골랐다.

4. 환경변수가 항상 이기는 것은 아니다. 처음에는 `DB_PASSWORD` 환경변수를 주면 무조건 그 값이 쓰인다고 생각했다. 틀렸다. `DB_PASSWORD`는 스프링 설정 키가 아니라 `application.yml`의 `${DB_PASSWORD:bready-local}` 자리를 채우는 재료일 뿐이다. 프로파일 파일이 `spring.datasource.password`를 값으로 직접 덮어쓰면 그 플레이스홀더 줄 자체가 버려지고, `DB_PASSWORD`는 어디에도 쓰이지 않는다. 환경변수가 설정 파일을 이기는 것은 키 이름이 일치할 때(`SPRING_DATASOURCE_PASSWORD`)뿐이다.

## 2026-10-12 · 0-2 Testcontainers 기반

**문제**

앱은 뜨게 됐지만 테스트가 띄우는 DB는 H2 인메모리였다. 이 프로젝트가 의존하는 것은 H2로 확인할 수 없다.

- `PlanRepository`에 MySQL 문법으로 쓴 native query가 있다.
- 비관적 락을 거는 조회가 5곳에 있다. 경계 지도에서 찾은 전환 경쟁 상태가 바로 이 락의 순서 문제인데, H2의 락은 InnoDB와 동작이 다르다.
- Redis는 꺼져 있어도 `contextLoads`가 통과하고 있었다. 연결을 실제로 쓰는 순간까지 미루기 때문이다.

H2에서 통과한 테스트를 근거로 "기존 동작이 유지된다"고 말할 수 없었다.

**선택지와 결정**

컨테이너를 테스트에 붙이는 방법은 세 가지를 놓고 봤다.

| 안 | 방법 | 버린 이유 또는 고른 이유 |
|---|---|---|
| A | 추상 베이스 클래스에 `static` 컨테이너를 두고 통합 테스트는 상속만 한다 | 채택. 테스트 클래스가 가장 단순하고 컨테이너가 전체에서 한 번만 뜬다 |
| B | `@TestConfiguration`에 컨테이너를 빈으로 두고 테스트마다 `@Import` | 테스트마다 `@Import`를 반복해야 하고, 빠뜨리면 설정이 다른 컨텍스트가 하나 더 뜬다 |
| C | 접속 정보를 전부 `@DynamicPropertySource`로 손으로 등록 | 동작은 다 보이지만 코드가 늘고 오타 여지가 생긴다 |

H2는 의존성째 지웠다. DB를 띄우는 테스트가 `contextLoads` 하나뿐이었고 메인 코드에 쓰는 곳이 없었다. 테스트 DB가 한 종류면 "어느 DB에서 통과했나"를 따질 일이 없다. 대가는 테스트를 돌리려면 Docker가 켜져 있어야 한다는 것이다.

**배운 것**

1. 컨테이너를 `static`으로 한 번만 띄우는 이유는 스프링의 컨텍스트 캐시 때문이다. 처음에는 컨테이너를 테스트 클래스마다 띄우면 서로 충돌할 것이라고 생각했는데, 포트가 매번 임의라서 충돌은 없다. 실제 문제는 반대쪽이다. 스프링은 설정이 같은 테스트끼리 컨텍스트를 재사용한다. 클래스마다 컨테이너를 내렸다 올리면 포트가 바뀌는데, 재사용된 컨텍스트의 DataSource는 이미 죽은 옛 포트를 보고 있다. 그래서 컨테이너의 수명을 컨텍스트 캐시의 수명(JVM 전체)에 맞춰야 한다.

2. 통합 테스트가 `application.yml`에 적힌 `localhost:3307`로 붙지 않는 이유는 테스트용 설정 파일 때문이 아니다. `application-test.yml`에는 DB 주소가 아예 없다. `@ServiceConnection`이 붙은 컨테이너에서 스프링 부트가 접속 정보를 직접 읽고, 이것이 설정 파일의 `spring.datasource.*`보다 먼저 쓰인다.

3. `@ServiceConnection`은 스프링 부트가 자동으로 만드는 연결에만 닿는다. Redis에는 못 썼다. `RedisConfig`가 `@Value`로 host와 port를 읽어 연결을 직접 만들기 때문이다. 그래서 `@Value`가 읽는 설정 값 자체를 바꿔 주는 `@DynamicPropertySource`를 썼다. 0-1의 OpenAI 건과 뿌리가 같다. 그때는 라이브러리가 만든 빈을 우리 스위치가 못 껐고, 이번에는 우리가 직접 만든 빈을 라이브러리 기능이 못 건드렸다. 자동 설정을 직접 만든 빈으로 대체하면 그 주변 편의 기능도 함께 포기하게 된다.

4. 테스트 DB는 매번 빈 컨테이너라서 스키마를 `create-only`로 만든다. `create-drop`으로 뒀더니 없는 테이블을 지우려는 경고가 쏟아졌다([T-004](TROUBLESHOOTING.md#t-004)).

5. "진짜 DB에 붙었다"도 테스트로 확인해야 한다. 설정을 잘못 써서 다른 DB에 붙어도 `contextLoads`는 통과한다. 그래서 `select version()`이 8.0인지, 테이블 엔진이 InnoDB인지, Redis 포트가 컨테이너의 임의 포트인지 확인하는 테스트를 따로 뒀다.

## 2026-10-12 · 0-3 핵심 흐름 통합 테스트

**문제**

기존 테스트는 Mockito 단위 테스트와 컨트롤러 슬라이스뿐이었다. 계층을 하나씩 따로 보기 때문에, 요청이 필터와 컨트롤러와 서비스를 거쳐 DB에 저장되고 그 결과가 다음 요청에 이어지는 것은 아무도 지키지 않았다. 앞으로 모듈 사이의 JPA 연관을 끊고 서비스를 떼어낼 텐데, 그때마다 "사용자가 겪는 흐름이 그대로인가"를 확인해 줄 것이 필요했다.

**선택지와 결정**

- 호출은 HTTP부터 한다. 서비스 메서드를 직접 부르는 편이 쓰기는 쉽지만, 나중에 Gateway를 앞에 세우고 모듈을 떼어낼 때 지켜야 하는 것은 HTTP 계약이다. 가입과 로그인도 HTTP로 해서 받은 JWT를 헤더에 싣는다. 그래서 보안 필터까지 함께 검증된다.
- 테스트 사이의 격리는 롤백이 아니라 비우기로 한다. 테스트에 `@Transactional`을 붙이면 편하지만 커밋이 일어나지 않는다. 이 프로젝트의 통계는 커밋 이후에 도는 리스너가 갱신하므로, 롤백 방식에서는 통계 검증이 영원히 실패한다.
- 범위는 성공 흐름 하나와 실패 셋이다. 실패 셋은 인증(401), 소유권(403), DB 유니크 제약(409)이 살아 있는지 지키는 최소선으로 골랐다.

검증하는 흐름은 가입, 로그인, 플랜 생성, 카테고리 추가, 후보 2개 등록, 트리거, 결정, 전환이다. 전환 뒤에 대표 후보가 두 번째로 바뀌었는지와 통계에 전환 1회가 잡혔는지를 본다.

**배운 것**

1. 이 흐름에는 외부 호출이 하나도 없었다. 후보 등록이 카카오를 부를 줄 알았는데, 장소 정보를 요청 본문으로 받는다. 그래서 mock 없이 끝까지 진짜로 돌릴 수 있었다. 외부에 의존하는 것은 장소 검색, 소셜 로그인, 이미지 업로드, AI 추천 네 가지이고 전부 가장자리에 있다. 가장자리부터 떼어낸다는 방향과 맞아떨어진다.

2. 비동기로 반영되는 값은 응답이 돌아온 시점에 아직 옛 값일 수 있다. 전환 API가 200을 돌려줘도 통계는 잠시 뒤에 바뀐다. 테스트에서는 `Thread.sleep` 대신 조건이 맞을 때까지 기다리는 Awaitility를 썼다. 이것은 테스트만의 사정이 아니라 지금 구조의 성질이다. 사용자도 전환 직후 통계 화면에서 옛 숫자를 볼 수 있다.

3. `foreign_key_checks`는 세션 변수다. 테이블을 비우려고 FK 검사를 끄는데, 끄기와 비우기와 켜기를 `JdbcTemplate`으로 각각 실행하면 커넥션 풀에서 서로 다른 커넥션을 받을 수 있다. 그러면 검사를 끈 커넥션과 비우는 커넥션이 달라서 FK 오류가 난다. 한 커넥션을 잡고 그 안에서 전부 실행해야 한다.

4. 격리가 되는지도 확인했다. 네 테스트 모두 플랜 생성 응답의 ID가 1이었다. truncate가 AUTO_INCREMENT까지 초기화하므로, 앞 테스트의 데이터가 남지 않았다는 증거가 된다.

5. 테스트를 쓰다가 트리거, 결정, 전환 API가 소유자를 확인하지 않는다는 것을 다시 확인했다. 토큰만 있으면 남의 플랜에 전환을 실행할 수 있다. 경계 지도에 적어 둔 문제이고, 플랜 모듈의 공개 API를 만드는 단계에서 고친다. 이번 테스트는 본인의 흐름만 지킨다.

## 2026-10-12 · 0-4 서비스 인자 로깅 제거

**문제**

`LoggingAspect`가 모든 서비스 메서드의 시작과 끝을 INFO로 남기면서, 시작 로그에 인자를 `toString()`으로 통째로 찍고 있었다.

- 문자열 인자는 그대로 찍힌다. `NaverAuthService.login(String code, String state)`의 OAuth 인가 코드가 평문으로 로그에 남고 있었다.
- 지금 로그인 요청 DTO는 `toString()`이 없는 일반 클래스라 `LoginRequest@1a2b3c` 같은 값만 찍힌다. 우연히 안전한 상태다. 이 DTO를 record로 바꾸는 순간 `LoginRequest[email=..., password=평문]`이 된다. DTO를 record로 통일하기로 했으므로 그 전에 이 로그부터 없애야 했다.
- 요청 하나에 서비스 호출 수의 두 배만큼 INFO 로그가 쌓였다.

**선택지와 결정**

| 안 | 방법 | 버린 이유 또는 고른 이유 |
|---|---|---|
| A | 인자를 빼고 시작·종료 로그를 DEBUG로 내린다. 예외 로그는 둔다 | 채택. 민감 정보가 남지 않고, 필요할 때 DEBUG를 켜면 흐름을 볼 수 있다 |
| B | 애스펙트를 통째로 지운다 | 예외 로그까지 사라진다 |
| C | 인자만 빼고 INFO를 유지한다 | 요청마다 찍히는 INFO가 그대로 남는다 |

**배운 것**

1. AOP로 "모든 메서드"에 로그를 거는 방식은 편하지만, 무엇이 찍히는지를 통제할 수 없다. 새 서비스 메서드를 만드는 사람은 자기 인자가 로그에 찍힌다는 것을 모른다. 민감 정보는 "찍지 말아야 할 것을 걸러내는" 방식이 아니라 "필요한 것만 골라 찍는" 방식이어야 안전하다. 기존 코드에도 파일이나 요청 객체를 걸러내는 목록이 있었지만, 그 목록에 없는 모든 타입은 그대로 찍혔다.

2. record는 `toString()`이 모든 필드를 출력한다. 편리한 기본 동작이 로그와 만나면 유출 경로가 된다. 로그 정책과 별개로, 비밀번호나 토큰을 담는 record는 `toString()`을 재정의해서 이중으로 막는다.

3. 로그 레벨은 "누가 언제 보는가"로 정한다. 요청마다 찍히는 흐름 로그는 개발 중에만 필요하므로 DEBUG이고, INFO는 운영에서 의미 있는 사건에만 쓴다.

4. 없앤 동작이 되돌아오지 않게 테스트로 고정했다. `LoggingAspectTest`는 시작 로그를 남길 때 `JoinPoint.getArgs()`가 한 번도 호출되지 않는 것을 확인한다. 누군가 인자 로깅을 다시 넣으면 이 테스트가 실패한다.

## 2026-10-12 · 1단계 경계 지도 확정

**문제**

다음 단계는 모듈 사이의 잘못된 참조를 끊는 작업인데, 무엇이 잘못된 참조인지는 경계를 어디에 긋느냐에 달려 있었다. ArchUnit 기준선은 패키지를 곧 모듈로 보고 위반을 435건으로 센다. 그대로 따르면 `trigger → plan` 참조도 끊어야 한다. 하지만 전환은 한 트랜잭션에서 trigger와 plan의 데이터를 함께 바꾼다. 경계를 정하지 않고 시작하면 끊지 않아도 되는 것을 끊고, 끊으면 안 되는 것까지 끊게 된다.

**선택지와 결정**

결정은 [ADR-0001](adr/0001-bounded-contexts-and-extraction-order.md)에 남겼다. 요약하면 이렇다.

| 결정 | 선택 | 버린 안과 이유 |
|---|---|---|
| trigger의 위치 | Planning에 합친다 | 따로 두면 전환이 두 서비스에 걸친다. 락이 서비스 경계를 넘지 못하고, 대표 변경과 이력 기록이 따로 커밋된다 |
| 장소 후보의 위치 | 후보는 Planning, 장소만 Place Catalog | place 패키지에 함께 두면 Catalog를 뗄 때 후보가 딸려 간다 |
| auth와 user | 하나의 Identity | 나누면 가입과 로그인마다 서비스 간 호출이 생기는데 얻는 것이 없다 |
| 추출 순서 | Place Catalog → Recommendation → Stats | Recommendation부터 하면 모놀리식에 내부 API를 먼저 열어야 하고, Stats부터 하면 첫 추출부터 메시지 유실 방지가 필요하다 |

감수한 것은 Planning이 테이블 8개를 가진 큰 컨텍스트가 된다는 점이다. 플랜, 후보, 트리거를 따로 배포하거나 따로 늘릴 수 없다.

**배운 것**

1. 바운디드 컨텍스트는 패키지나 테이블 수로 정하는 것이 아니라 "함께 바뀌어야 하는 것"으로 정한다. 서비스를 나누면 DB가 나뉘고, 그러면 트랜잭션과 락과 JOIN이 그 선을 넘지 못한다. 경계를 긋는다는 것은 그 선에서 한 번에 맞추기를 포기한다는 뜻이다.

2. 경계를 정할 때 던지는 질문에는 순서가 있다. 먼저 나누면 안 되는 이유를 찾는다. 한 트랜잭션으로 같이 커밋되어야 하는가, 같은 행을 락으로 줄 세우는가, 생명주기가 묶여 있는가. 이 중 하나라도 해당하면 같은 경계다. 그다음에 나눠도 되는 이유를 본다. 잠깐 틀려도 되는가, 같은 단어가 다른 뜻인가, 쓰는 쪽이 하나인가, 죽어도 핵심 흐름이 도는가.

3. 질문의 답은 코드에서 찾는다. `@Transactional` 메서드가 쓰는 테이블, `@Lock`이 잠그는 행, 패키지를 넘는 JPA 연관, JOIN의 이유, 호출 방향. 이 다섯 가지를 표로 만들면 감이 아니라 근거로 말할 수 있다.

4. 락이 서비스 경계를 넘지 못하는 이유는 락이 한 커넥션의 트랜잭션에 묶여 있기 때문이다. DB가 나뉘면 커넥션과 트랜잭션도 따로다. 락은 트랜잭션이 끝나는 순간 풀리므로, 한 서비스가 락을 쥔 채 다른 서비스의 처리를 기다리게 할 수도 없다. 전환의 경쟁 상태를 한 트랜잭션 안에서 고칠 수 있는 것도 trigger와 plan이 같은 DB에 있기 때문이다. (이때는 락 순서만 바꾸면 된다고 생각했는데, 실제로는 그것만으로 부족했다. 2-3 항목에 적었다.)

5. 경계를 다시 그으니 숫자가 달라졌다. 435건 중 약 189건은 같은 컨텍스트 안의 참조라서 끊을 필요가 없고, 실제 경계 위반은 약 246건이다. 대부분 stats와 recommendation에서 나온다. 작업량의 43%가 결정 하나로 사라졌다.

6. 장애는 불리는 쪽에서 부르는 쪽으로 퍼진다. 처음에는 서비스를 떼어내면 떼어낸 쪽만 죽고 모놀리식은 영향이 없다고 생각했다. 틀렸다. 모놀리식이 Place Catalog를 호출하는 기능(장소 검색, 후보 등록, 규칙 기반 추천)은 Catalog가 죽으면 같이 안 된다. 호출하지 않는 기능(로그인, 플랜 수정, 전환, 통계)만 계속 된다. 반대로 모놀리식이 죽어도 Catalog는 멀쩡하다. Place Catalog를 첫 추출로 고른 이유인 "나가는 의존이 없다"는 것이 이 뜻이다. 장애가 한 방향으로만 퍼진다.

7. 동기와 비동기는 서로 다른 것을 내준다. 통계 갱신을 전환과 같은 트랜잭션에 넣으면 숫자는 항상 맞지만, 전환이 통계만큼 느려지고 통계에서 예외가 나면 전환까지 롤백된다. 지금처럼 커밋 뒤 비동기로 하면 전환은 통계와 무관하게 성공하지만 숫자가 잠깐 틀릴 수 있고 유실되면 계속 틀린다. 처음에는 이 둘을 섞어서, 동기로 하면 보상이 필요하다고 생각했다. 보상은 나눠서 처리할 때의 문제다.

8. 보상은 저절로 생기지 않는다. 지금 통계 리스너는 실패하면 ERROR 로그만 남긴다. 재시도도 보상도 없다. 다음에 같은 플랜에서 트리거나 전환이 일어나면 처음부터 다시 세기 때문에 그때 맞아질 뿐이다. 유실을 막는 장치(Outbox, 재시도)는 직접 만들어야 하고, Stats를 떼는 단계에서 다룬다.

## 2026-10-12 · 2-1 죽은 코드 제거

**문제**

경계를 끊는 작업을 시작하려는데, 끊을 대상 목록에 아무도 쓰지 않는 코드가 섞여 있었다. `PlanStatsJoinService` 하나가 위반 기준선에서 15줄을 차지했다. 쓰이지 않는 코드의 참조를 정리하는 것은 낭비이므로 먼저 지워야 했다.

**선택지와 결정**

`PlanStatsJoinService`는 단순히 버려진 코드가 아니었다. README의 성능 개선 기록에 나오는 "개선 전" 구현이다. JOIN 방식과 사전 집계 방식을 부하 테스트로 비교한 뒤 API를 사전 집계로 통합했는데, 그때 URL만 사라지고 서비스 클래스가 남았다.

- 남겨 두는 안: 개선 전 코드가 눈에 보인다. 하지만 호출할 URL이 이미 없어서 실험을 재현할 수 없고, 살아 있는 코드처럼 보여 혼란을 준다.
- 지우는 안(채택): 개선 전 구현은 커밋 이력에 있다는 것을 설계서에 적어 두었다. 비교가 다시 필요하면 이력에서 복원한다.

지운 것은 클래스 4개와 그것들만 쓰던 쿼리 3개, 테스트에 남아 있던 쓰이지 않는 mock 필드 하나다. 203줄을 지우고 추가한 줄은 없다.

**배운 것**

1. 죽은 코드인지는 종류마다 확인 방법이 다르다. 서비스는 주입받는 곳이 없으면 호출되지 않으므로 참조 검색으로 충분하다. 컨트롤러는 아무도 참조하지 않아도 스프링이 URL에 연결해 실행한다. 살아 있는 컨트롤러도 참조는 0이다. 그래서 컨트롤러는 매핑 메서드가 있는지를 봐야 한다. 처음에는 컨트롤러도 참조하는 파일만 찾으면 된다고 생각했다.

2. 클래스를 지우면 그 클래스만 쓰던 것이 연쇄로 죽는다. 쿼리 메서드는 호출하는 곳이 없어도 컴파일이 되므로 조용히 남는다. 지우려는 클래스가 부르던 메서드를 하나씩 따라가며 다른 사용처가 있는지 확인했고, 그 과정에서 원래 목록에 없던 죽은 쿼리 하나를 더 찾았다.

3. 지우는 과정에서 숨어 있던 버그가 드러났다. 통계 응답의 `categoryTypes` 필드를 채우는 코드가 지운 클래스에만 있었다. 지금 API가 쓰는 구현은 이 필드를 채우지 않아 항상 null이다.

4. 위반 기준선은 사람이 고치지 않는다. 테스트를 돌리자 ArchUnit이 기록해 둔 위반 중 더는 없는 16줄을 스스로 지웠다. 기준선은 줄어들기만 하고 늘어나지 못한다. 

5. 테스트의 mock은 "안 쓰는 mock"이 아니라 "안 쓰는 stub"이 검사 대상이다. 선언만 한 mock 필드는 테스트를 실패시키지 않아서 지운 서비스의 흔적이 테스트에 오래 남아 있었다. 동작을 걸어 두고 쓰지 않았다면 Mockito가 실패시켰을 것이다.

## 2026-10-12 · 2-2 컨텍스트 기준으로 모듈 재정의

**문제**

경계를 ADR로 정했지만 코드와 테스트는 그 결정을 모르고 있었다. ArchUnit은 패키지를 곧 모듈로 봐서 같은 Planning 안인 `trigger → plan` 참조까지 위반으로 셌다. 그리고 `place` 패키지 하나에 Planning의 것(장소 후보)과 Place Catalog의 것(장소, 검색)이 섞여 있었다. 여기서 Place Catalog는 플랜의 카테고리와 다른 말이다. 장소 자체의 정보 모음, 즉 `places` 테이블과 카카오 검색을 가리킨다.

**선택지와 결정**

| 안 | 방법 | 버린 이유 또는 고른 이유 |
|---|---|---|
| A | 패키지는 두고 ArchUnit에서만 컨텍스트로 묶는다 | `place`가 둘로 갈리지 않아 클래스 이름 패턴으로 구분해야 한다 |
| B | 후보 관련 클래스만 `plan`으로 옮기고 나머지는 ArchUnit에서 컨텍스트로 묶는다 | 채택. 경계와 어긋난 패키지는 `place` 하나뿐이었다 |
| C | 패키지 전체를 컨텍스트 이름으로 재배치한다 | 100개 넘는 파일이 움직이는데 얻는 것은 이름뿐이다 |

URL은 바꾸지 않았다. 후보가 쓰던 에러 다섯 개는 `plan` 쪽 enum으로 옮기되 숫자 코드는 그대로 뒀다.

**배운 것**

1. 패키지와 URL은 따로 움직인다. 컨트롤러를 다른 패키지로 옮겨도 URL은 `@RequestMapping`이 정하므로 그대로다. 패키지는 우리끼리의 정리이고 URL은 클라이언트와의 약속이다. 에러 코드도 같다. 응답에 나가는 것은 enum 이름이 아니라 숫자라서, enum을 다른 클래스로 옮겨도 숫자가 같으면 계약은 깨지지 않는다.

2. 호출 방향과 의존 방향은 다를 수 있다. 후보 서비스(Planning)가 장소 저장 서비스(Place Catalog)를 부르는 것은 원한 방향이다. 그런데 장소 저장 메서드가 파라미터로 후보 등록 요청 DTO를 받고 있었다. 부르는 것은 Planning인데, 타입을 아는 것은 Catalog 쪽이었다. Catalog의 코드에 Planning을 import하는 줄이 생긴다. 이대로 Catalog를 떼어내면 Catalog를 빌드할 때 Planning의 코드가 필요해지고, 따로 배포할 수 없다. 서비스를 잘못 떼어낸 것이 된다. Catalog가 자기 타입을 받게 하고 변환은 부르는 쪽이 하도록 고쳤다. 불리는 쪽은 부르는 쪽을 몰라야 한다.

3. 이 문제는 옮기기 전에는 보이지 않았다. 두 클래스와 DTO가 모두 `place` 패키지에 있어서 같은 모듈 안의 호출로 보였기 때문이다. 경계를 패키지로 드러내자 잘못된 방향이 import 한 줄로 눈에 들어왔다. 구조를 실제 경계에 맞추는 일은 정리 이상의 효과가 있다. 숨어 있던 의존을 보이게 만든다.

4. 추정과 측정은 달랐다. 1단계에서 실제 경계 위반을 약 231건으로 추정했는데, 테스트가 센 값은 274건이었다. `plan → place` 참조 대부분이 후보일 것이라고 봤지만 실제로는 `PlaceCategoryType` enum이었다. 이 enum은 플랜의 카테고리 타입이면서 카카오 카테고리 코드도 들고 있어 두 컨텍스트에 걸쳐 있다. 표를 눈으로 나눈 추정은 방향을 잡는 데 쓰고, 결정의 근거는 측정한 값으로 삼아야 한다.

5. ArchUnit은 위반을 문장으로 기억하고 그 문장에 패키지 이름이 들어 있다. 클래스를 옮기면 같은 위반이 "사라진 위반과 새 위반"으로 보여 테스트가 실패한다. 기준선에서 패키지 이름만 바꿨고, 줄 수가 같고 다른 변경이 없는 것을 diff로 확인했다. 기준선을 손으로 고치지 않는다는 규칙의 목적은 새 위반을 몰래 인정하지 않는 것이다. 주소만 바꾸는 것은 그 목적에 어긋나지 않지만, 확인 없이 하면 구별할 수 없게 된다.

## 2026-10-12 · 2-3 전환 경쟁 상태 수정

**문제**

전환과 후보 삭제가 동시에 일어나면 삭제된 후보가 대표로 지정될 수 있었다. 전환은 "바꿀 후보가 살아 있는가"를 먼저 확인하고 그다음에 `category_states` 락을 잡는다. 삭제도 같은 락을 잡는다. 전환이 확인을 마친 직후 삭제가 락을 얻어 후보를 지우고 커밋하면, 전환은 락을 얻은 뒤 다시 확인하지 않고 그 후보를 대표로 지정한다.

trigger를 Planning에 합치기로 한 근거가 "한 DB 안에서 락으로 정합성을 지킬 수 있다"였으므로, 실제로 그렇게 고칠 수 있는지 보여야 했다.

**선택지와 결정**

처음에는 답이 정해져 있다고 생각했다. 락을 먼저 잡고 그 뒤에 확인하면 된다. 그래서 결론을 내리기 전에 재현 테스트부터 만들었고, 수정안 세 가지를 차례로 돌려 봤다.

| 안 | 방법 | 전환 응답 | 결과 |
|---|---|---|---|
| 수정 전 | | 200 | 버그 재현 |
| A | 락 조회를 후보 확인보다 위로 옮긴다 | 200 | 고쳐지지 않음 |
| B | A + 후보 확인을 잠금 읽기로 | 400 | 막았지만 에러가 틀림 |
| C | A + 격리 수준을 READ COMMITTED로 | 404 | 통과 |

C를 골랐다. B는 후보 행에 락을 더 잡는데, 카테고리 타입 변경은 후보를 먼저 잠그고 상태를 나중에 잠근다. 전환이 그 반대 순서로 잠그면 데드락이 날 수 있다. C는 락이 늘지 않는다. 대가는 이 메서드만 격리 수준이 다르다는 것이고, 주석과 재현 테스트로 지킨다.

**배운 것**

1. 락을 잡았는데도 옛 데이터를 볼 수 있다. MySQL의 기본 격리 수준인 REPEATABLE READ에서 트랜잭션은 처음 일반 조회를 한 순간의 모습(스냅샷)을 끝까지 본다. 전환은 맨 처음에 결정을 조회하므로 그때 스냅샷이 만들어진다. 그 뒤 삭제가 커밋되고 전환이 락을 얻어도, 후보를 확인하는 조회는 스냅샷을 본다. 스냅샷은 DB 전체의 것이 아니라 그 트랜잭션 자신의 것이다. 잠금 읽기(`FOR UPDATE`)만 스냅샷이 아닌 최신 커밋을 본다.

2. 락과 격리 수준은 서로 다른 문제를 푼다. 락은 누가 먼저 들어갈지를 정하고, 격리 수준은 들어간 뒤 무엇을 볼지를 정한다. 이번 수정에 둘 다 필요했던 이유다. 락을 먼저 잡지 않으면 확인과 변경 사이에 삭제가 끼어든다. 이때는 확인한 순간의 값이 최신이었어도 소용이 없다. 락을 먼저 잡아도 격리 수준이 그대로면 최신이 아닌 값을 본다. 처음에는 이 둘을 같은 문제로 봤고, 락 순서만 바꾸면 된다고 다른 문서에 적기까지 했다.

3. 동시성 버그는 재현하기 전에는 고쳤다고 말할 수 없다. 재현 테스트가 없었다면 A안을 적용하고 끝냈을 것이다. 코드를 읽어서는 맞아 보였기 때문이다.

4. 재현은 순서를 직접 만들어야 한다. 요청을 동시에 여러 번 보내면 버그가 나는 순서가 만들어질 때도 있고 아닐 때도 있어서, 통과해도 고쳐진 것인지 운이 좋았던 것인지 알 수 없다. 테스트가 `category_states` 락을 먼저 쥐고, 삭제 요청과 전환 요청을 차례로 보내 둘 다 대기하게 한 뒤 락을 풀었다. 두 요청이 실제로 대기 중인지는 MySQL의 락 대기 목록을 조회해 확인했다.

5. B안에서 에러가 틀리게 나온 것도 같은 원리였다. 후보 확인은 잠금 읽기라 "없다"를 제대로 봤지만, 바로 다음에 "없는 것인지 다른 카테고리의 것인지"를 가르는 조회가 일반 조회여서 다시 스냅샷을 봤다. 한 메서드 안에서 조회마다 보는 시점이 달라질 수 있다.

6. 버그 하나를 찾으면 같은 모양을 다른 곳에서도 찾아본다. "읽고, 락을 잡고, 다시 확인하지 않는다"는 모양을 같은 락을 쓰는 코드에서 찾았더니 대표 지정에도 있었다. 대표 지정은 어느 카테고리의 락을 잡을지 알려면 후보를 먼저 읽어야 해서 순서를 바꿀 수 없다. 대신 락을 얻은 뒤 후보가 살아 있는지 다시 확인

## 2026-10-12 · 2-4 소유권 검증 추가

**문제**

로그인만 하면 남의 플랜을 바꿀 수 있었다. 후보 등록, 대표 지정, 후보 삭제, 트리거 생성, 결정, 전환 여섯 API가 요청한 사용자를 아예 받지 않았다. 컨트롤러에 사용자 정보를 받는 파라미터가 없었고, 서비스는 누가 불렀는지 모른 채 처리했다. 다른 사용자의 토큰으로 여섯 API를 호출하는 테스트를 먼저 썼고, 전부 200으로 성공하는 것을 확인했다.

트리거 API의 Swagger 문서에는 "403: 플랜 소유자 아님"이 원래부터 적혀 있었다. 문서에는 있고 코드에는 없었다.

**선택지와 결정**

| 안 | 방법 | 버린 이유 또는 고른 이유 |
|---|---|---|
| A | 플랜 엔티티에 `validateOwner(userId)`를 두고 서비스가 부른다 | 채택. 규칙이 한 곳에 있고 엔티티만으로 테스트할 수 있다 |
| B | 조회 쿼리에 소유자 조건을 넣는다 | 남의 것이면 "없음"(404)이 되어, 403을 주는 기존 API와 응답이 갈린다 |
| C | 어노테이션이나 AOP로 공통 처리한다 | 플랜을 찾는 경로가 API마다 다르다. 전환은 결정 → 트리거 → 플랜, 후보 삭제는 후보 → 카테고리 → 플랜이다. 공통화하기 어렵고 동작이 숨는다 |

같은 소유자 비교(`if (!plan.getOwnerId().equals(userId))`)가 이미 10곳에 복사돼 있었다. 이 중 Planning 안의 8곳을 함께 정리했다.

**배운 것**

1. 인증과 인가는 다른 단계다. 인증은 "누구인가"이고 토큰을 확인하는 필터가 한다. 인가는 "이 사람이 이 자원에 이 일을 해도 되는가"이고 자원을 조회해 봐야 알 수 있다. 여섯 API는 인증은 통과했지만 인가가 없었다. 로그인을 요구한다고 해서 안전한 것이 아니다.

2. 요청한 사용자는 토큰에서 꺼낸 값만 믿는다. 요청 본문이나 경로에 사용자 ID를 받으면 요청하는 사람이 마음대로 쓸 수 있다. 컨트롤러가 `@CurrentUser`로 받아 서비스에 넘긴다.

3. 리팩터링할 때 응답에 나가는 값은 건드리지 않는다. 8곳을 모두 `validateOwner`로 바꾸려다가 카테고리 API 4곳이 다른 에러 코드(4201)를 던지고 있는 것을 발견했다. `validateOwner`는 4002를 던진다. 똑같이 바꾸면 코드는 깔끔해지지만 응답의 에러 코드가 달라지고, 그 숫자로 분기하는 프론트엔드가 영향을 받는다. 그래서 판단만 하는 `isOwnedBy`를 따로 두고 카테고리 쪽은 기존 에러를 그대로 던지게 했다. 처음에는 카테고리 쪽이 다른 이유를 "플랜에서 이미 확인하고 와서"라고 생각했는데, 실제 이유는 밖으로 나가는 값이 달랐기 때문이다.

4. 소유권 확인은 다른 검증보다 먼저 한다. 순서를 바꿔도 뒤에서 막기는 하므로 남의 플랜이 바뀌지는 않는다. 새는 것은 정보다. 남의 결정 ID를 넣어 보고 "KEEP 결정이라 전환할 수 없다"나 "이미 전환됐다"는 에러를 받으면 남의 플랜 상태를 알 수 있다. 소유권을 먼저 보면 무엇을 넣어도 "권한 없음"만 돌아온다.

5. 테스트는 거절 응답만 보지 않고 데이터도 본다. 403이 나왔더라도 그 전에 무언가 저장됐을 수 있다. 각 테스트는 후보 수, 대표 후보, 삭제 여부, 트리거·결정·전환 기록 수가 그대로인지 DB에서 확인한다.

6. 경계를 먼저 정한 것이 이 작업을 단순하게 만들었다. trigger와 장소 후보를 Planning에 합쳐 두었기 때문에, 소유권 확인은 다른 컨텍스트에 묻는 일이 아니라 같은 컨텍스트 안에서 연관을 따라가는 한 줄이 됐다.

## 2026-10-13 · 2-5 Planning → Place Catalog 공개 API

**문제**

Place Catalog(장소 정보 모음, `places` 테이블과 카카오 검색)를 4단계에서 처음으로 떼어낼 계획인데, 지금 모양으로는 뗄 수 없었다. Planning이 Catalog의 속을 직접 쓰고 있었기 때문이다.

- 장소 후보(`PlaceCandidate`)가 장소 엔티티를 `@ManyToOne Place place`로 들고 있었다.
- 플랜 상세 조회가 `plan_categories ⋈ place_candidates ⋈ places`를 한 쿼리로 읽었다. DB가 나뉘면 실행할 수 없는 쿼리다.
- 플랜 상세의 작성자 닉네임을 얻으려고 `PlanService`가 `UserRepository`를 직접 주입받았다.
- 카테고리 타입 enum(`PlaceCategoryType`)이 `place.domain`에 있어서 Planning의 엔티티와 DTO 7곳이 Catalog의 내부 패키지를 import했다.

ArchUnit 기준선으로 Planning의 경계 위반은 49건이었다.

**선택지와 결정**

정할 것이 세 가지였다.

플랜 상세가 장소 이름과 주소를 어디서 얻을 것인가.

| 안 | 방법 | 버린 이유 또는 고른 이유 |
|---|---|---|
| A | 후보를 등록할 때 장소 정보를 후보 테이블에 복사해 둔다 | Catalog가 죽어도 상세가 보인다는 장점은 Catalog를 실제로 떼어낸 뒤에야 의미가 있다. 지금은 컬럼 추가와 기존 데이터 채우기만 비용으로 남는다 |
| B | 후보는 장소의 ID만 갖고, 조회할 때 Catalog에 묻는다 | 채택. 스키마가 그대로이고 쿼리는 하나만 늘어난다. 대가는 서비스로 떼었을 때 Catalog 장애가 플랜 상세로 번진다는 것이고, 이것은 4단계에서 직접 죽여 보고 다시 정한다 |

카테고리 타입 enum을 누가 가질 것인가. 뜻으로는 플랜의 것이라 Planning으로 옮기고 싶었지만, 이 enum은 카카오 검색 키워드와 카테고리 코드도 들고 있어서 Catalog의 검색 코드가 쓴다. Planning으로 옮기면 Catalog가 Planning을 import하게 되고, Catalog를 첫 추출로 고른 근거("Catalog는 아무도 부르지 않는다")가 깨진다. Catalog 소유로 두고 공개 패키지로 옮겼다.

다른 컨텍스트에 내놓는 창구의 모양. 기존 서비스를 그대로 부르는 안, 쓰는 쪽에 포트와 어댑터를 두는 안, 내놓는 쪽에 `api` 패키지를 두는 안 중 마지막을 골랐다. `place.api`에 인터페이스 `PlaceCatalogApi`와 주고받는 값(`PlaceInfo`), enum을 두고, 구현은 `place.service`에 둔다. Planning은 `place.api`만 import한다. 작성자 닉네임도 같은 모양(`user.api.UserApi`)으로 바꿨다.

**배운 것**

1. 경계를 넘을 때는 엔티티가 아니라 ID와 값이 넘어간다. 후보는 `Long placeId`만 갖고, 장소 정보가 필요하면 `PlaceInfo`라는 값 묶음을 받는다. 엔티티를 넘기면 받는 쪽이 그 엔티티의 지연 로딩이나 다른 필드를 건드릴 수 있고, 서비스가 나뉘면 그 클래스 자체가 받는 쪽 코드에 없다.

2. 컬럼은 그대로 두고 매핑만 바꿨다. `@ManyToOne @JoinColumn(name = "place_id")`를 `@Column(name = "place_id") Long placeId`로 바꾸면 DB는 달라지지 않는다. 연관관계는 코드가 테이블을 보는 방식이지 테이블 자체가 아니다. 그래서 데이터 이관 없이 경계를 먼저 끊을 수 있었다. 로컬 DB의 FK 제약은 남아 있고 4단계에서 없앤다.

3. JOIN을 끊으면 조회는 "모아서 한 번에 묻기"가 된다. 플랜 상세는 후보들의 `placeId`를 모아 `getPlaces(ids)`를 한 번 부르고 `Map`으로 조립한다. 후보마다 부르면 지금은 쿼리가 후보 수만큼 나가고, 서비스로 떼면 네트워크 왕복이 후보 수만큼 생긴다. 처음에는 서버가 나뉘면 이 호출이 메시징 큐로 간다고 생각했다. 틀렸다. 응답에 장소 이름을 넣어야 하므로 답을 기다리는 동기 호출이다. 큐는 답을 기다리지 않아도 되는 일에 쓴다.

4. 구현이 하나뿐인 인터페이스는 보통 만들지 않는데, 이 인터페이스는 둔다. 4단계에서 구현이 "DB 조회"에서 "HTTP 호출"로 바뀌는 자리이기 때문이다. 부르는 쪽은 인터페이스만 알아서 그때 코드를 고치지 않아도 된다. 지금 당장의 쓸모는 "여기까지만 써도 된다"는 선을 코드로 긋는 것이고, ArchUnit 규칙이 그 선을 넘으면 빌드를 실패시킨다.

5. 공개 패키지는 자기 모듈의 내부를 import하지 않게 했다. `PlaceInfo.from(Place)`처럼 쓰면 편하지만, 그러면 `api` 패키지가 엔티티에 묶이고 나중에 이 패키지를 계약으로 떼어 갈 때 엔티티까지 따라온다. 변환은 구현 서비스가 한다.

6. 구조를 바꾸기 전에 응답을 먼저 고정했다. 후보 등록과 플랜 상세의 JSON을 필드 하나하나 확인하는 테스트를 옛 코드에서 먼저 통과시키고, 그 테스트가 그대로 통과하는 것을 보면서 바꿨다. 쓰다가 후보 등록이 201이 아니라 200을 돌려준다는 것도 알았다. 규칙과는 다르지만 프론트엔드와의 약속이라 그대로 뒀다.

7. 한 번에 바꾼 양이 많아서 내가 따라가지 못했다. enum 이동으로 import만 바뀐 파일 15개와 로직이 바뀐 파일 6개가 한꺼번에 보여서, `PlacePersistenceService`가 어디로 갔는지조차 헷갈렸다. 이름만 `PlaceCatalogService`로 바뀐 것이었다. 기계적인 이동과 로직 변경은 따로 나눠서 보는 편이 낫다.

## 2026-10-13 · 2-6 Stats·Recommendation → Planning 공개 API

**문제**

2-5에서 Planning이 남의 내부를 쓰는 것은 다 끊었지만, 반대로 Planning의 내부를 남이 쓰는 것이 199건 남아 있었다. 전부 Recommendation과 Stats였다.

- 통계 서비스 6개가 Planning의 리포지토리 4개를 주입받아 쿼리 메서드 11개를 직접 불렀다.
- 추천은 트리거 ID 하나를 받아 `Trigger → Plan → PlanCategory → CategoryState → PlaceCandidate`를 엔티티로 따라갔고, 소유권 검증(`plan.getOwnerId().equals(userId)`)도 직접 했다. 엔티티는 포트의 파라미터로 어댑터 4개까지 흘러갔다.
- `TriggerType`과 `DecisionType`을 쓰는 것만으로 71건이었다.
- 전환과 트리거를 알리는 이벤트 클래스가 받는 쪽인 `stats.event`에 있어서, 보내는 쪽인 trigger가 stats를 import했다.
- 공통 예외 핸들러가 파라미터 이름(`"file"`, `"period"`)을 보고 어느 모듈의 요청인지 추측해 그 모듈의 에러를 줬다.

2-5에서 한 번에 너무 많이 바꿔 내가 따라가지 못했기 때문에, 이번에는 네 묶음으로 나누고 묶음마다 멈췄다.

**선택지와 결정**

통계가 Planning의 데이터를 얻는 방법이 가장 큰 결정이었다.

| 안 | 방법 | 버린 이유 또는 고른 이유 |
|---|---|---|
| A | Planning이 조회용 공개 API를 열고 Stats가 부른다 | 채택. 변경이 작고 동작이 그대로다. 대가는 Stats를 떼었을 때 통계 화면이 Planning에 동기로 의존한다는 것 |
| B | Stats가 이벤트를 받아 자기 테이블에 쌓고, 조회는 자기 테이블만 읽는다 | 목적지는 이쪽이다. 하지만 지금 이벤트는 메모리에만 있어서 유실되면 숫자가 계속 틀린다. 유실을 막는 Outbox와 Kafka는 5단계의 일이다 |

A는 B로 가는 중간 단계다. 5단계에서 Stats를 떼어낼 때 조회 API 호출을 자기 테이블 조회로 바꾼다.

추천에 내주는 API는 리포지토리를 본뜬 작은 조회 여러 개 대신, "이 사용자의 이 트리거에 대한 추천 재료"를 한 번에 내주는 조회 하나로 만들었다. 추천은 5단계에서 떼어낼 대상이라 호출 횟수가 그대로 네트워크 왕복 횟수가 된다.

공통 예외 핸들러는 처음에 "모듈마다 자기 컨트롤러 전용 핸들러를 둔다"로 가려 했다. 그런데 `file` 파트를 파일 업로드와 프로필 이미지 두 모듈의 컨트롤러가 함께 써서, 컨트롤러 단위로 자르면 한쪽 응답이 달라졌다. `global`이 인터페이스를 정하고 `s3`가 구현하는 방식으로 바꿨다.

**배운 것**

1. 리포지토리 직접 주입이 나쁜 방법인 것은 아니다. 지금까지 그렇게 개발해 왔고, 한 서비스 안에서 트랜잭션과 JOIN을 함께 쓰기에는 그게 맞다. 이번에도 같은 컨텍스트 안에서는 그대로 직접 주입한다. `TriggerContextService`는 Planning 안이라 `PlanCategoryRepository`를 그대로 쓴다. 인터페이스로 바꾸는 것은 떼어낼 경계를 넘을 때만이다. 한 트랜잭션, 한 JOIN, 한 락으로 묶여야 하면 같은 경계 안에 둔다.

2. 인터페이스로 바꾼다고 결합이 끊기는 것은 아니다. 처음에는 "도메인끼리 결합을 끊는 작업"이라고 이해했다. 정확히는 내부에 대한 결합을 약속에 대한 결합으로 좁히는 것이다. Stats는 여전히 Planning을 부른다. 달라진 것은 Planning이 테이블이나 쿼리를 바꿔도 인터페이스만 지키면 Stats가 모른다는 것과, 서비스가 나뉘어도 성립한다는 것이다. 결합이 실제로 사라지는 것은 이벤트와, 5단계에서 Stats가 자기 테이블을 가질 때다.

3. 인터페이스가 서비스를 떼어낼 때 하는 일. 떼어내면 쓰는 쪽은 같은 인터페이스를 HTTP 클라이언트로 한 번 더 구현하고, 내놓는 쪽은 지금의 구현에 컨트롤러를 붙인다. 인터페이스의 메서드가 HTTP API 목록이 되고 record가 주고받는 JSON이 된다. 두 서비스가 무엇을 주고받을지를, 한 프로세스 안에서 테스트가 지켜 주는 상태로 먼저 정해 두는 것이다.

4. 헥사고날 아키텍처와는 뿌리가 같고 방향이 다르다. 둘 다 구현이 아니라 인터페이스에 의존한다. 헥사고날은 쓰는 쪽이 "나는 이런 게 필요하다"를 포트로 선언하고, 여기서는 내놓는 쪽이 "나는 이것만 제공한다"를 선언한다. 쓰는 쪽이 여럿이면 내놓는 쪽이 선언하는 편이 중복이 없다. 반대로 공통 예외 핸들러는 헥사고날 방향이 맞았다. `global`은 어떤 모듈도 알면 안 되므로 `global`이 인터페이스를 정하고 모듈이 구현한다.

5. 주입을 끊어도 반환 타입으로 내부가 새어 나갈 수 있다. 리포지토리 안에 선언된 프로젝션 인터페이스(`RecentSwitchActivityRow`)를 그대로 넘기면 Stats는 결국 리포지토리를 import한다. 그 타입의 모양은 쿼리의 `select ... as` 별칭과 짝이라, Planning이 쿼리를 고치면 Stats가 깨진다. 메서드뿐 아니라 주고받는 타입도 공개 패키지의 것이어야 한다.

6. 소유권 검증은 데이터 주인이 하고, 거절은 데이터를 내주기 전에 한다. Planning이 `ownerId`를 돌려주고 추천이 비교하게 만들 수도 있었다. 그러면 비교하기도 전에 남의 플랜 정보가 추천으로 넘어가고, Planning을 쓰는 컨텍스트마다 같은 비교를 다시 짜야 한다. 하나가 빠뜨리면 구멍이다. 2-4에서 고친 구멍이 그렇게 생긴 것이었다.

7. 동기 호출과 메시징 큐는 쓰임이 다르다. 처음에는 서비스가 나뉘면 통계 화면이 Planning에 큐로 묻는다고 생각했다. 틀렸다. 답을 받아야 응답을 만들 수 있는 일은 동기 호출이다. 큐로 하는 일은 묻는 것이 아니라, 일이 일어날 때마다 미리 받아 자기 테이블에 쌓아 두는 것이다. 그러면 화면을 그릴 때 물을 필요 자체가 없어진다. 또 하나 잘못 알고 있던 것은 지금의 통계 갱신이 동기라고 생각한 것이다. `@Async`와 `AFTER_COMMIT`으로 다른 스레드에서 도는 비동기다. 답을 기다리지 않아도 되는 이유는 전환 응답에 통계 숫자가 들어가지 않고, 통계가 실패해도 전환은 성공이어야 하기 때문이다.

8. 느린 상대를 기다리는 동안 쥐고 있는 자원이 바닥나면 무관한 기능까지 멈춘다. 장소 추천은 읽기 트랜잭션 안에서 외부를 호출해서 DB 커넥션을 쥔 채로 기다린다. 커넥션 풀은 기본 10개다. Catalog가 응답하지 않고 타임아웃도 없으면 장소 추천 요청 10개가 풀을 다 채우고, Catalog를 부르지도 않는 카테고리 추천이 커넥션을 빌리지 못해 줄을 선다. 서버가 죽지는 않지만 멈춘 것과 같다. 타임아웃과 서킷브레이커가 필요한 이유이고 5단계에서 직접 재현해 본다.

9. `@ExceptionHandler` 메서드 안에서 던진 예외는 다른 핸들러가 받지 않는다. 공통 핸들러에는 잘못된 `period`에 통계 에러(6003)를 던지는 분기가 있었다. 응답을 고정하는 테스트를 먼저 써 보니 실제로는 본문 없는 400이 나가고 있었다. 핸들러 안에서 던지면 스프링 기본 처리로 넘어가기 때문이다. 이 분기는 한 번도 동작한 적이 없었다. 코드를 읽고 믿은 것과 실제 응답이 달랐고, 테스트를 먼저 쓰지 않았다면 "응답은 그대로"라고 틀리게 말했을 것이다. 응답이 바뀌는 수정이라 이번에는 고치지 않고 기록만 했다.

10. 규칙 설명 문구가 기준선의 열쇠다. 커밋하기 전에 ArchUnit 규칙의 `because(...)` 문구를 다듬었더니 경계 규칙 9개가 전부 새 규칙으로 취급되어 기준선이 통째로 새로 만들어졌다. `allowStoreCreation=false`는 기준선 폴더가 없을 때만 막는다. 이번에는 새 기준선의 건수가 옛 기준선에서 그사이 고친 71건을 뺀 값과 같은 것을 대조해서 새로 인정된 위반이 없음을 확인했다. 확인하지 않았다면 그사이에 생긴 위반이 조용히 묻혔을 것이다.

결과: 컨텍스트 사이의 경계 위반이 199건에서 0건이 됐다. 2단계 전체로는 274건에서 0건이다. 테스트는 185개가 통과하고, 응답을 고정하는 통합 테스트가 다섯 종류(플랜 상세와 후보 등록, 통계, 카테고리 추천, 장소 추천, 에러 응답) 생겼다. 이 단계의 결정은 ADR-0002에 모았다.

## 2026-10-14 · 3-1 모놀리식을 monolith/로 이동

**문제**

4단계에서 Place Catalog를 떼어내기 전에 앞단에 Gateway를 세워야 한다. 그런데 레포 루트 전체가 모놀리식이었다. 이 상태로 Gateway를 추가하면 `src/` 옆에 `gateway/`가 붙고, 루트의 `build.gradle`이 모놀리식이면서 전체의 부모가 된다. 떼어낸 서비스가 모놀리식의 부속처럼 보인다. 구조 자체가 "서비스는 독립돼 있다"를 말해 주지 못했다.

**선택지와 결정**

| 안 | 방법 | 버린 이유 또는 고른 이유 |
|---|---|---|
| A | 루트는 모놀리식 그대로, `settings.gradle`에 `include 'gateway'` | 처음 추천안이었다. 파일을 옮기지 않아도 되고 하네스가 경로에 묶인 곳(31곳)을 고칠 필요가 없다. 하지만 구조가 비대칭이라 버렸다 |
| B | 루트 `settings.gradle`로 묶은 멀티 모듈 | 대칭이지만 공유 모듈을 쉽게 만들 수 있어서 서비스가 코드로 다시 묶이기 쉽다 |
| C | commerce-msa처럼 서비스마다 독립 Gradle 프로젝트, 루트에는 빌드 없음 | 채택. 서로의 코드를 가져다 쓸 방법이 아예 없다. 모놀리식은 빌드 파일과 `src/`를 그대로 한 층 내리면 된다. 대가는 전체를 한 명령으로 빌드할 수 없고, 빌드 설정이 서비스마다 중복된다는 것 |

처음에는 이동 비용만 보고 A를 추천했다. 이 레포는 구조가 결과물이라 보기 좋은 대칭은 미관이 아니라 요구사항이었다. commerce-msa를 다시 열어 보니 서비스마다 `gradlew`까지 가진 독립 프로젝트였고, 루트에는 빌드 파일이 없었다.

이동과 하네스 수정은 커밋을 나눴다. 이동 커밋은 내용 변경이 0이다.

**배운 것**

1. 파일을 옮기면 경로를 가정한 보호 장치는 에러 없이 꺼진다. Stop 훅은 루트에 `gradlew`가 없으면 "검사할 수 없는 환경"으로 보고 통과시킨다. 린트는 경로에서 모듈 이름을 못 뽑으면 경계 검사를 건너뛴다. 쓰기 가드는 `build.gradle` 경로가 맞지 않으면 승인 없이 쓰게 둔다. 셋 다 실패하지 않고 조용히 통과한다. 에러가 나는 고장은 바로 보이지만 이런 고장은 보호가 사라진 줄도 모른 채 지나간다. 그래서 이번 조각의 실제 작업은 이동이 아니라 꺼진 장치를 찾는 일이었다.

2. 회귀 테스트도 옛 경로를 들고 있으면 계속 통과한다. 훅 테스트의 케이스가 `src/main/...` 경로였기 때문에, 훅이 실제 경로(`monolith/src/main/...`)에서 꺼져 있어도 초록이었다. 케이스를 실제 경로로 옮기고, 서비스 디렉터리 아래의 빌드 파일과 기준선 케이스를 추가했다. Stop 훅은 포맷이 깨진 임시 파일을 만들어 실제로 막는지 확인했다. 통과한다는 결과만으로는 검사를 했는지 안 했는지 구분할 수 없다.

3. git은 이동을 기록하지 않는다. 커밋마다 내용의 스냅숏만 남기고, 비교할 때 사라진 파일과 생긴 파일의 내용이 얼마나 비슷한지를 보고 rename으로 추정한다. 그래서 `git mv`가 아니라 `mv`로 옮겨도 304개가 전부 rename이 됐다. 옮기면서 내용을 조금씩 고쳤다면 작은 파일은 삭제와 추가로 갈라져 히스토리가 끊기고, 리뷰어는 어디를 실제로 고쳤는지 찾을 수 없었을 것이다.

4. 독립 프로젝트의 불편함은 의도된 것이다. 4단계에서 Catalog도 응답 봉투와 에러 형식이 필요하다. 멀티 모듈이었다면 공통 모듈을 만들어 함께 썼을 것이다. 편하지만 공통 모듈을 한 줄 고쳐도 모든 서비스를 다시 배포해야 하고, 도메인 코드가 공통 모듈로 흘러 들어가기 쉽다. 서비스 사이에서 지켜야 하는 것은 같은 클래스가 아니라 같은 HTTP 응답 모양이다.

5. 루트에 빌드를 두지 않으면 도구가 먼저 알아챈다. IntelliJ가 루트를 Gradle 프로젝트로 연결하고 있어서 "Gradle 빌드가 없다"는 오류가 났다. `.gitattributes`의 `/gradlew`처럼 루트에 고정된 패턴도 있었다. 앞의 `/`는 루트 파일만 뜻해서, 그대로 두었다면 `monolith/gradlew`는 LF 강제에서 빠졌을 것이다.

결과: 이동한 파일 304개가 전부 rename으로 기록됐고, `monolith/`에서 테스트 189개가 이동 전과 같이 통과한다. 훅 회귀 테스트는 163개가 통과한다.

## 2026-10-14 · 3-2 gateway-service와 전체 경로 라우팅

**문제**

4단계에서 Place Catalog를 떼어내면 `/api/v1/places/**`의 일부가 다른 프로세스로 가야 한다. 클라이언트가 주소 두 개를 알게 되면 외부 계약이 바뀐다. 그래서 떼기 전에 앞단 입구(Gateway)를 세우고, 지금은 모든 요청을 모놀리식으로 보내면서 "끼워도 응답이 같다"를 먼저 증명하기로 했다. 확인해야 할 것은 두 가지였다. Gateway를 지난 요청이 모놀리식에 어떻게 도착하는지, 그리고 클라이언트가 받는 응답이 정말 같은지.

**선택지와 결정**

| 결정 | 버린 안 | 고른 안과 대가 |
|---|---|---|
| Gateway 구현 | nginx. 지금 하는 일(전부 8080으로)은 설정 몇 줄로 똑같이 되지만, 라우팅을 JUnit으로 고정하기 어렵고 5·6단계에 붙일 서킷브레이커·JWT 필터를 Java로 쓸 수 없다 | Spring Cloud Gateway. 대가는 JVM 프로세스 하나가 더 뜨는 것 |
| 검증 | 가짜 모놀리식 자동 테스트만, 또는 실제 기동 비교만 | 둘 다. WireMock 테스트가 계약을 고정하고, 실제 기동 비교는 내가 떠올리지 못한 경우를 찾는다. 실제로 CORS 문제는 두 번째에서만 나왔다 |
| X-Forwarded 헤더 | `trusted-proxies`로 켜기, `PreserveHostHeader`로 Host 유지 | 끈 채로. 모놀리식에 Host나 클라이언트 IP를 쓰는 코드가 0건이다. 대가는 모놀리식이 모든 요청을 Gateway에서 온 것으로 본다는 것 |
| CORS | 모놀리식에 그대로(처음 결정), 양쪽에 두고 중복 헤더 제거 | Gateway 한 곳. 대가는 브라우저가 `:8080`을 직접 부르면 CORS 헤더가 없다는 것. Gateway가 유일한 입구라는 전제와 맞다 |
| 하네스 | 서비스 목록을 직접 적기 | `gradlew`가 있는 최상위 디렉터리를 서비스로 본다. verify는 전부, Stop 훅은 고친 서비스만 |

**배운 것**

1. Gateway는 리버스 프록시라서 연결이 두 개다. 클라이언트와 Gateway 사이, Gateway와 모놀리식 사이. Gateway는 받은 요청을 라우트의 `uri`로 다시 보내고 받은 응답을 그대로 돌려준다. 모놀리식을 끄고 요청하니 Gateway 로그에 `Connection refused: localhost:8080`이 찍히고 500이 나왔다. 8080에 연결을 시도한 것은 클라이언트가 아니라 Gateway였다. 이 500은 모놀리식이 아니라 Gateway가 지어낸 응답이라 형식도 `CommonResponse`가 아니다. 5단계 서킷브레이커는 이 두 번째 연결의 실패만 세야 한다.

2. 라우트는 위에서부터 비교해서 먼저 맞은 하나를 탄다. 지금은 `Path=/**` 하나뿐이라 전부 모놀리식으로 간다. 4단계에서는 더 좁은 라우트를 그 위에 끼운다. `/api/v1/places/candidates/**`는 Planning 소유라서 `/api/v1/places/**`보다 위에 있어야 한다. 순서가 바뀌면 후보 요청이 그 API가 없는 Catalog로 가서 404가 난다. 이렇게 좁은 라우트가 늘수록 모놀리식으로 가는 몫이 줄어드는 것이 Strangler Fig다. 서비스를 고르는 것(라우팅)과 같은 서비스의 여러 대 중에 고르는 것(로드 밸런싱)은 다른 일이다. 지금은 앞의 것만 한다.

3. 처음에는 Gateway가 원래 Host를 `X-Forwarded-Host`로 넘긴다고 생각했다. 틀렸다. 헤더를 그대로 찍는 서버를 띄워 보니 X-Forwarded 헤더가 하나도 없었다. Gateway 4.3부터는 `trusted-proxies`를 설정해야 이 필터가 생긴다. 예전처럼 무조건 붙이면 클라이언트가 직접 넣은 `X-Forwarded-For`까지 믿어서 IP를 위조할 수 있기 때문이다. 내가 알던 것은 옛 버전의 기본값이었다. 켤 때도 `.*`가 아니라 실제 프록시 주소만 믿어야 한다.

4. 처음에는 CORS를 모놀리식에 두기로 했다. Gateway는 통과만 시키면 된다고 생각했다. 틀렸다. 실제 기동 비교에서 모놀리식이 허용하는 Origin의 preflight가 `:8080`에서는 200, `:8000`에서는 403이었다. 403 응답에 모놀리식의 보안 헤더가 없어서 모놀리식까지 가지 않았다는 것을 알았다. WebFlux의 핸들러 매핑은 preflight를 라우트로 넘기지 않고 그 자리에서 판정한다. 모놀리식이 아무리 허용해도 preflight는 거기까지 가지 않는다. 그래서 CORS를 Gateway로 옮기고 모놀리식에서는 껐다. 양쪽에 두면 실제 응답에 `Access-Control-Allow-Origin`이 두 번 붙어 브라우저가 거부한다. 프록시를 끼우면 "그대로 전달된다"고 믿은 것 중 일부는 프록시가 직접 처리한다.

5. 가짜 서버 테스트는 내가 떠올린 경우만 검사한다. WireMock 테스트는 경로·쿼리·본문·`Authorization`·에러 응답이 그대로 오가는 것을 모두 통과했지만, preflight 시나리오가 없어서 CORS 문제는 잡지 못했다. 실제로 띄워서 같은 요청을 양쪽에 보내 보고서야 드러났다. 자동 테스트와 실제 기동 비교를 둘 다 하기로 한 이유가 여기서 나왔다. 찾은 뒤에는 그 경우를 `GatewayCorsTest`로 옮겨, 실패하는 것을 먼저 보고 고쳤다.

6. 테스트가 변화를 정말 잡는지도 확인해야 한다. X-Forwarded 테스트는 `trusted-proxies`를 잠깐 켜서 실패하는 것을 봤다. CORS 테스트를 처음 썼을 때는 "모놀리식이 받은 요청이 없다"를 검사했는데, WireMock의 요청 기록이 테스트끼리 공유돼서 다른 테스트의 GET이 잡혔다. 실행 순서에 따라 결과가 달라지는 테스트였다. 의도한 대로 "OPTIONS 요청이 없다"로 좁혔다.

7. 하네스가 "검사하지 않음"과 "통과"를 똑같이 보여 주면 보호가 꺼진 것을 아무도 모른다. Stop 훅이 `monolith`로 고정돼 있어서 gateway의 Java는 출력 없이 통과하고 있었다. 이제 고친 Java의 첫 디렉터리에 `gradlew`가 있으면 그 서비스를 검사하고, 없으면 검사하지 못했다고 알린다. 막지 않고 알리기만 하는 이유는, 검사를 못 한 곳에서는 위반이라는 증거가 없기 때문이다. 막으면 결국 훅을 통째로 끄게 된다. 같은 구멍이 하나 남아 있다. ArchUnit은 `architecture` 테스트가 있는 서비스에서만 돌리는데, 도메인이 없는 gateway의 건너뜀과 4단계 Catalog에서 ArchUnit을 빠뜨린 건너뜀이 화면에서 똑같다. 4단계에서 닫는다.

결과: Gateway 테스트 8개, monolith 테스트 189개, 훅 회귀 테스트 165개가 통과한다. 같은 요청 12종을 모놀리식 직접과 Gateway 경유로 비교해 9종은 상태·헤더·본문이 같고, preflight는 CORS를 옮긴 뒤 200이 됐다. 남은 차이는 상태 문구, 헤더 이름 대소문자, 연결 관리 헤더뿐이다.
