# ADR-0002: 컨텍스트 사이는 내놓는 쪽의 공개 API 패키지로만 오가고, 데이터는 조회할 때 묻는다

- **상태**: 채택
- **날짜**: 2026-10-13
- **로드맵 단계**: 2
- **관련 설계서**: [design/2-modular-monolith.md](../design/2-modular-monolith.md)

## 맥락

[ADR-0001](0001-bounded-contexts-and-extraction-order.md)에서 컨텍스트를 여섯으로 정하고 Place Catalog → Recommendation → Stats 순으로 떼어내기로 했다. 그런데 컨텍스트끼리 서로의 내부를 직접 쓰고 있어서 그대로는 하나도 뗄 수 없었다. 컨텍스트 단위로 센 ArchUnit 기준선으로 274건이었다([경계 지도](../architecture/context-map.md) 11번).

- 다른 컨텍스트의 리포지토리를 주입받았다. 통계 서비스 6개가 Planning의 리포지토리 4개를, 추천이 4개를, 플랜 상세가 `UserRepository`를 썼다. 서비스가 나뉘면 남의 DB에 직접 붙는 것이 된다.
- 다른 컨텍스트의 엔티티를 연관관계로 들고 있었다. `PlaceCandidate.place`(`@ManyToOne Place`)가 그랬고, 플랜 상세 조회는 `plan_categories ⋈ place_candidates ⋈ places`를 한 쿼리로 읽었다. DB가 나뉘면 실행할 수 없다.
- 엔티티가 경계를 넘어 흘러 다녔다. 추천의 포트가 `List<PlanCategory>`를 파라미터로 받아 어댑터까지 넘겼다.
- 값만 담은 enum이 남의 내부 패키지에 있었다. `PlaceCategoryType`, `TriggerType`, `DecisionType`을 쓰는 것만으로 위반이 100건을 넘었다.
- 이벤트 클래스가 받는 쪽(`stats.event`)에 있어서 보내는 쪽(trigger)이 받는 쪽을 import했다.

정해야 할 것은 세 가지였다. 컨텍스트가 다른 컨텍스트에 무엇을 어떤 모양으로 내놓을지, JOIN을 끊은 뒤 남의 데이터를 어떻게 얻을지, 통계처럼 남의 데이터로 화면을 만드는 컨텍스트를 지금 어디까지 분리할지다.

## 선택지

**1. 공개 API의 모양**

| | 선택지 A | 선택지 B | 선택지 C |
|---|---|---|---|
| 방법 | 기존 서비스를 그대로 부르고 반환만 엔티티에서 record로 바꾼다 | 내놓는 쪽이 `{module}.api` 패키지에 인터페이스·값 record·enum을 둔다. 구현은 `service`에 | 쓰는 쪽이 포트를 선언하고 어댑터가 상대를 부른다 |
| 얻는 것 | 변경이 가장 작다 | 쓰는 쪽은 `api` 패키지만 import한다. 서비스로 떼면 구현만 원격 호출로 바뀐다. "여기까지만 공개"를 빌드로 강제할 수 있다 | 쓰는 쪽이 상대의 타입을 전혀 모른다 |
| 잃는 것 | 무엇이 공개이고 무엇이 내부인지 구분이 없다 | 인터페이스, 값 record, 구현 클래스가 늘어난다 | 쓰는 컨텍스트마다 포트와 어댑터가 생긴다. Catalog와 Planning은 쓰는 쪽이 둘 이상이다 |
| 되돌리기 비용 | 낮다 | 중간. 2-5와 2-6의 모든 호출부가 이 모양을 따른다 | 높다 |

**2. JOIN을 끊은 뒤 남의 데이터를 얻는 방법 (플랜 상세의 장소 정보)**

| | 선택지 A | 선택지 B |
|---|---|---|
| 방법 | 후보를 등록할 때 장소 이름·주소·좌표를 후보 테이블에 복사해 둔다 | 후보는 장소의 ID만 갖고, 조회할 때 ID를 모아 공개 API를 한 번 부른다 |
| 얻는 것 | 조회가 자기 테이블만 읽는다. Catalog가 죽어도 플랜 상세가 보인다 | 스키마가 그대로다. 쿼리는 하나만 늘어난다 |
| 잃는 것 | 컬럼 추가와 기존 행 채우기, 데이터 중복 | 서비스로 떼면 이 호출이 네트워크를 타고 Catalog 장애가 플랜 상세로 번진다 |
| 되돌리기 비용 | 컬럼 삭제 | 컬럼 추가와 기존 행 채우기 |

**3. Stats가 Planning의 데이터를 얻는 방법**

| | 선택지 A | 선택지 B |
|---|---|---|
| 방법 | Planning이 조회용 공개 API를 열고 Stats가 부른다 | Stats가 이벤트를 받아 자기 테이블에 쌓고 조회는 자기 테이블만 읽는다 |
| 얻는 것 | 변경이 작고 동작이 그대로다 | Planning이 죽어도 통계가 보인다 |
| 잃는 것 | 서비스로 떼면 통계 화면이 Planning에 동기로 의존한다 | 이벤트가 유실되면 숫자가 계속 틀린다. 지금 이벤트는 메모리에만 있다 |
| 되돌리기 비용 | 낮다 | 높다. 유실을 막을 Outbox와 메시지 브로커가 먼저 있어야 한다 |

## 결정

**1은 B.** 컨텍스트가 다른 컨텍스트에 내놓는 것은 내놓는 쪽의 `{module}.api` 패키지에 둔다. 인터페이스(`PlaceCatalogApi`, `PlaceSearchApi`, `UserApi`, `PlanQueryApi`, `ActivityQueryApi`, `TriggerContextApi`), 주고받는 값 record, 값만 담은 enum, 다른 컨텍스트가 듣는 이벤트(`trigger.api.event`)가 여기에 있다. 다른 컨텍스트는 이 패키지만 import하고, ArchUnit의 `apiOnly` 규칙이 그 밖을 쓰면 빌드를 실패시킨다. `api` 패키지는 자기 모듈의 엔티티를 import하지 않는다. 결정적인 이유는 쓰는 쪽이 여럿이라는 것(C는 쓰는 쪽마다 포트가 생긴다)과, 인터페이스가 4·5단계에서 구현이 실제로 바뀌는 자리라는 것이다.

**2는 B.** 엔티티 연관은 ID 참조로 바꾸고(`PlaceCandidate.placeId`), 필요한 값은 조회할 때 ID를 모아 한 번에 묻는다. 복사해 두는 안이 막아 주는 고통은 Catalog를 실제로 떼어낸 뒤에 생기고, 그때 직접 죽여 보고 정할 수 있다. B에서 A로 가는 길은 막히지 않는다.

**3은 A.** Stats는 Planning의 조회 API를 부른다. B가 목적지인 것은 맞지만 이벤트 유실을 막는 장치가 5단계의 일이다.

조회 API는 리포지토리 메서드를 하나씩 본뜨지 않고, 쓰는 쪽이 한 번에 필요한 것을 묶어 내준다(`getPlaces(ids)`, `getTriggerContext(userId, triggerId)`). 호출 횟수가 서비스로 떼었을 때의 네트워크 왕복 횟수가 되기 때문이다. 소유권 검증처럼 데이터 주인만 할 수 있는 판단은 공개 API 안에서 끝내고, 거절은 데이터를 내주기 전에 한다.

한 가지 예외가 있다. `global`은 어떤 모듈도 알면 안 되므로 방향이 반대다. `global`이 인터페이스(`MissingPartErrorCaseProvider`)를 정하고 모듈이 구현한다.

## 결과

- 좋아지는 것:
  - 컨텍스트 사이의 리포지토리·엔티티 직접 사용이 274건에서 0건이 됐다. 공개 패키지 밖을 쓰는 것도 0건이고, 새로 생기면 빌드가 실패한다.
  - 모듈을 넘는 JPA 연관, 모듈을 넘는 JOIN, 받는 쪽 패키지의 이벤트가 없어졌다. trigger ⇄ stats 순환이 한 방향이 됐다.
  - 4단계에서 Place Catalog를 떼어낼 때 Planning과 Recommendation의 코드는 바뀌지 않고 `PlaceCatalogApi`·`PlaceSearchApi`의 구현만 원격 호출로 바꾸면 된다. 두 서비스가 주고받을 내용이 인터페이스와 record로 이미 정해져 있다.
  - 응답 JSON과 에러 코드는 바뀌지 않았다. 바꾸기 전에 응답을 고정하는 통합 테스트를 먼저 썼다.
- 감수하는 것 (트레이드오프):
  - 의존이 사라진 것은 아니다. 내부에 대한 의존이 공개 API에 대한 의존으로 좁아졌을 뿐이다. Stats와 Recommendation은 여전히 Planning이 살아 있어야 동작한다.
  - JOIN과 한 트랜잭션을 포기했다. 플랜 상세는 쿼리가 하나 늘었고, 후보 등록은 장소 저장과 후보 저장이 원자적이지 않다.
  - 조회 API가 쓰는 쪽의 화면 모양을 따라간다. `ActivityQueryApi`는 메서드가 10개이고 사실상 Stats 전용이다.
  - `PlaceCategoryType`을 Planning과 Catalog가 함께 쓴다. 서비스로 떼면 값이 추가될 때 양쪽을 함께 배포해야 한다.
  - 통계 이벤트는 여전히 메모리에만 있어 유실될 수 있다. 이번에는 이벤트 클래스의 위치만 옮겼다.
  - `global`이 `AuthErrorCase`를 쓰는 6건은 남겼다. 인증은 6단계 전에 손대지 않기로 했다.
- 나중에 다시 볼 조건 (이 결정을 뒤집을 신호):
  - 4단계에서 Place Catalog를 떼어낸 뒤 Catalog 장애나 지연이 플랜 상세를 못 쓰게 만들면, 장소 정보를 후보에 복사해 두는 안(2의 A)으로 간다.
  - 5단계에서 Stats를 떼어낼 때 조회 API를 이벤트 기반의 자기 읽기 모델로 바꾼다(3의 B). 그때 `ActivityQueryApi`의 대부분은 없어진다.
  - `PlaceCategoryType`에 값을 추가하는 일이 잦아지고 그때마다 두 서비스를 함께 배포해야 하면, Planning의 값 enum과 Catalog의 검색 매핑으로 쪼갠다.
  - 한 요청에서 다른 컨텍스트를 부르는 횟수가 늘어 응답이 눈에 띄게 느려지면, 그 데이터를 한 트랜잭션·한 JOIN으로 함께 써야 하는 것은 아닌지, 즉 경계가 잘못 그어진 것은 아닌지 ADR-0001부터 다시 본다.
