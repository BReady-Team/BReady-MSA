# ADR-0004: Place Catalog를 코드 → 데이터 순서로 떼어내고, 전용 DB와 Flyway로 소유를 끝낸다

- **상태**: 채택
- **날짜**: 2026-11-12
- **로드맵 단계**: 4
- **관련 설계서**: [design/4-place-catalog-extraction.md](../design/4-place-catalog-extraction.md)

## 맥락

[ADR-0001](0001-bounded-contexts-and-extraction-order.md)에서 Place Catalog를 처음 떼어내기로 했다. 나가는 의존이 0이고 호출 방향이 모놀리식 → Catalog 한쪽뿐이라서다. [ADR-0002](0002-public-api-package-per-module.md)로 다른 컨텍스트는 `place.api`만 쓰게 됐고, [ADR-0003](0003-strangler-facade-gateway.md)으로 클라이언트 앞에 Gateway가 섰다. 남은 것은 실제로 다른 프로세스, 다른 DB로 옮기는 일이었다. 옮기기 전에 드러난 문제는 이랬다.

- 후보 추가(`PlaceCandidateService.createCandidate`)는 `@Transactional` 안에서 장소 등록(`register`)을 불렀다. 등록이 HTTP가 되면 Catalog를 기다리는 동안 DB 커넥션을 쥐고 있게 된다.
- 플랜 상세와 추천은 `getPlaces`로 장소를 조회했다. 테스트에서 `places` 행을 지우자 플랜 상세는 500, 추천은 `IllegalStateException`으로 500이었다. Catalog가 죽으면 플랜 보기까지 죽는 구조였다.
- `places`는 모놀리식과 같은 MySQL에 있었고, `place_candidates.place_id → places` 외래키가 걸려 있었다. 모놀리식은 root로 붙으니 언제든 `places`를 JOIN할 수 있었다.
- 장소 검색(`GET /api/v1/places/search`)은 로그인이 필요하다. Catalog에는 인증이 없다.

## 선택지

**1. 떼어내는 순서**

| | 한 번에(코드·DB 함께) | 코드 먼저, 데이터 나중 | 데이터 먼저(모놀리식 안에서 데이터소스 분리) |
|---|---|---|---|
| 얻는 것 | 조각 수가 적다 | 한 조각에 새 문제가 하나씩 생긴다: 원격 호출(4-1), 트랜잭션·읽기(4-2), 데이터(4-3) | DB 분리를 먼저 겪는다 |
| 잃는 것 | 실패하면 원인이 네트워크인지 데이터인지 가리기 어렵다 | 4-2~4-3 사이 DB를 공유한다(쓰는 쪽은 Catalog뿐) | 모놀리식 안에 데이터소스가 둘이 되는 임시 구조를 만들고 다시 지운다 |
| 되돌리기 비용 | 높다 | 낮다(조각마다 되돌릴 수 있다) | 중간 |

**2. 플랜 상세·추천이 장소 정보를 얻는 방법**

| | 매번 Catalog 조회 | 조회 + 실패 시 장소 정보 없이 | 후보에 장소 스냅샷 복사 |
|---|---|---|---|
| 얻는 것 | 항상 최신 | 플랜 상세가 죽지는 않는다 | Catalog 장애와 분리. `getPlaces` API가 필요 없다 |
| 잃는 것 | Catalog가 죽으면 플랜 상세도 죽는다 | 화면에 빈 장소가 나온다 | 컬럼 6개와 기존 행 백필 |
| 되돌리기 비용 | — | 낮다 | 중간 |

**3. 후보 추가의 트랜잭션**

| | 그대로(HTTP를 트랜잭션 안에서) | 트랜잭션 밖으로 빼기 | 후보 먼저 저장 후 장소 등록 |
|---|---|---|---|
| 잃는 것 | 네트워크를 기다리는 동안 커넥션을 쥔다 | 뒤 단계가 실패하면 쓰이지 않는 장소 한 줄이 남는다 | 등록이 실패하면 없는 장소를 가리키는 후보가 남아 보상 로직이 필요하다 |

**4. Catalog DB를 두는 곳**

| | 같은 서버의 별도 스키마 + 전용 계정 | 스키마 분리 후 DB 분리(두 단계) | 별도 MySQL 컨테이너 |
|---|---|---|---|
| 얻는 것 | 컨테이너가 늘지 않는다 | 멈출 수 없는 운영 환경에서 쓰는 경로를 연습한다 | 다른 서버의 테이블은 SQL로 볼 수 없어 JOIN이 구조적으로 불가능하다 |
| 잃는 것 | 함께 죽고, root로 붙는 모놀리식은 여전히 JOIN할 수 있다 | 잠깐 멈춰도 되는 로컬에서는 이관을 두 번 한다 | 컨테이너 하나만큼의 메모리 |

**5. 스키마 관리와 데이터 이관**

| | `ddl-auto: update` 유지 | 기존 테이블을 옮기고 Flyway baseline | 새 빈 DB에 Flyway `V1` + `validate`, 데이터는 일회성 스크립트 |
|---|---|---|---|
| 얻는 것 | 할 일이 없다 | 덤프를 그대로 쓴다 | 테스트와 로컬이 같은 `V1`을 실행해 스키마의 출처가 하나다. 틀리면 기동이 막힌다 |
| 잃는 것 | 스키마 변경 기록이 없고, 틀린 타입을 고치지도 알리지도 않는다 | `ddl-auto`가 남긴 쓰지 않는 컬럼(`deleted_at`)까지 따라온다 | 이관 스크립트를 따로 써야 한다(id 보존, 지문 비교) |

## 결정

**1. 코드 먼저, 데이터 나중. 네 조각으로 나눈다.** 4-1 검색(DB 없음), 4-2 저장·조회를 HTTP로, 4-3 전용 DB와 이관, 4-4 백업 삭제와 정리. 결정적인 이유는 한 조각에 새 문제가 하나씩만 생겨서 실패의 원인을 가릴 수 있다는 것이다. DB를 공유하는 동안에도 `places`에 쓰는 쪽은 Catalog뿐이라 소유권은 처음부터 Catalog에 있었다.

**2. 외부 입구는 모놀리식에 남긴다.** Gateway가 검색을 Catalog로 바로 보내면 인증 없이 누구나 검색할 수 있다. 인증은 6단계 전에 손대지 않으므로, 모놀리식이 로그인을 확인하고 Catalog를 내부 호출한다(`Gateway → 모놀리식 → Catalog`).

**3. 부르는 쪽은 그대로 두고 구현만 바꾼다.** `place.api`의 인터페이스는 그대로이고, 구현이 메서드 호출에서 `RestClient` + `@HttpExchange` HTTP 어댑터로 바뀌었다. 의존성 추가가 없고 동기 코드와 맞는다. 네트워크가 끼면서 생긴 실패는 어댑터가 맡는다. 닿지 못하면 503 `5031`, 상대의 오류 응답은 상태·코드·문구를 그대로 전달한다. 타임아웃은 합으로 맞췄다(Catalog의 카카오 호출 최악 7초 < 모놀리식이 Catalog를 기다리는 8초). 거꾸로면 카카오 오류가 "Catalog 연결 불가"로 보고된다.

**4. 공통 코드(`CommonResponse`, `ErrorCase` 등)는 필요한 것만 복사한다.** 서비스 사이에서 지킬 것은 같은 클래스가 아니라 같은 JSON 모양이다. 공유 라이브러리는 한 줄을 고쳐도 모든 서비스를 다시 빌드해야 하고 도메인 코드가 흘러 들어가기 쉽다. ADR-0003에서 "4단계에서 다시 정한다"고 남긴 질문의 답이다.

**5. 읽기는 복사로, 쓰기는 트랜잭션 밖의 호출로 끊는다.** 장소는 수정 메서드도 API도 없고 같은 외부 ID로 다시 등록하면 그대로 돌려준다. 그래서 복사본이 낡지 않는다. 후보에 `PlaceSnapshot`을 두고, 추천의 기준 위치도 스냅샷에서 만든다(`TriggerContextApi.getRepresentativePlace`). 후보 추가는 검증(읽기 트랜잭션) → 등록(트랜잭션 없음) → 저장(쓰기 트랜잭션, 카테고리 행을 잠그고 다시 검증)으로 나누고, DB 작업은 별도 빈(`PlaceCandidateTransactionHandler`)에 둔다. 장소를 먼저 커밋하면 뒤가 실패해도 쓰이지 않는 장소 한 줄이 남을 뿐이라 보상이 필요 없다.

**6. 별도 MySQL 컨테이너 `catalog-mysql`, 새 빈 DB에 Flyway `V1` + `ddl-auto: validate`.** 결정적인 이유는 JOIN이 규칙이 아니라 구조로 불가능해진다는 것과, 스키마를 만드는 쪽이 Flyway 하나가 된다는 것이다. Hibernate는 엔티티와 테이블이 맞는지 검사만 한다. 새 DB라 baseline이 필요 없다.

**7. 데이터는 일회성 스크립트로 id를 보존해 옮기고, 백업은 내용이 같은지 확인한 뒤 지운다.** DB가 갈라지면 외래키가 없고, 두 테이블을 잇는 것은 숫자 id뿐이다. id가 틀려도 에러가 나지 않는다. 그래서 이관 스크립트가 원본과 결과의 지문(행 내용 md5)과 다음 id를 직접 확인한다. 옛 테이블은 바로 지우지 않고 `places_legacy`로 이름을 바꿔 두었다가, 4-4에서 같은 지문으로 Catalog와 비교한 뒤 지웠다.

**8. 모놀리식에 남은 `place` 패키지는 지우지 않는다.** 남은 것은 장소 기능이 아니라 Catalog를 부르는 쪽이다. 계약(`place.api`), 그 HTTP 구현(`place.external`), 외부 입구(`PlaceSearchController`)가 남았고, plan·recommendation·trigger의 17개 파일이 이 계약을 쓴다.

## 결과

- 좋아지는 것:
  - 모놀리식은 `places`를 읽지도 쓰지도 않고, 같은 DB에 그 테이블이 없다. `place` 패키지에는 엔티티·리포지토리가 없다.
  - Catalog를 끈 실제 기동에서 플랜 상세는 200이고, 후보 추가와 추천은 500이 아니라 원인을 알려 주는 503 `5031`이다. 후보·장소는 생기지 않는다.
  - Catalog 스키마는 `V1`에 기록돼 있고, 테스트(Catalog 53개)도 같은 `V1` 위에서 돈다. `V1`의 컬럼 타입을 틀리면 `validate`가 기동을 막는다.
  - 이관과 백업 삭제가 같은 지문(`5 rows / md5 3a389a29…`)으로 이어져, 이관 뒤 데이터가 바뀌지 않았다는 것까지 확인했다.
- 감수하는 것 (트레이드오프):
  - `place_candidates.place_id`가 Catalog에 실제로 있는 id인지 DB는 보장하지 않는다.
  - 장소 검색은 Gateway → 모놀리식 → Catalog로 한 번 더 거친다.
  - Catalog 응답 오류 코드 4104·4105가 모놀리식 User 코드와 겹친 채로 클라이언트에 전달된다.
  - 후보 저장이 실패하면 쓰이지 않는 장소가 남는다(무해하다고 보고 정리하지 않는다).
  - 모놀리식은 여전히 `ddl-auto: update`이고, Catalog는 root 계정으로 DB에 붙는다.
  - 이관은 앱을 멈추고 하는 로컬 일회성 절차다. 멈출 수 없는 환경에서는 쓸 수 없다.
- 나중에 다시 볼 조건 (이 결정을 뒤집을 신호):
  - Catalog가 장소를 지우거나 합치거나 수정하게 되면 스냅샷이 낡는다. 그 사실을 모놀리식에 알리는 이벤트가 필요하다(5단계 Kafka 대상).
  - 6단계에서 Gateway가 JWT를 확인하면 검색을 Catalog로 바로 보내고 `PlaceSearchController`를 지운다.
  - 5단계에서 Catalog의 503을 어떻게 다룰지(재시도·차단·대체 응답) 정한다.
  - 모놀리식에서 `ddl-auto`로 못 하는 스키마 변경이 반복되면 Flyway를 넣는다. 기존 DB라 baseline이 필요하다.
  - 서비스마다 복사한 공통 코드가 자주 함께 바뀌면 복사를 다시 따진다. 다만 공유 라이브러리보다 계약 테스트를 먼저 본다.
  - 공개 API(`place.api.PlaceSearchApi`)와 Swagger 문서 인터페이스(`{Domain}Api`)의 이름이 겹친다. 7단계 구조 통일에서 이름 체계를 정한다.
