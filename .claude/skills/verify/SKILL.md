# /verify — 검증과 증거

"됐다"고 말하지 않는다. 아래 출력이 곧 답이다.

## 1. 빌드 검증
```bash
.claude/scripts/verify.sh          # 포맷 → 컴파일 → 전체 테스트
.claude/scripts/verify.sh --fast   # 포맷 → 컴파일 (구현 중간 확인용)
```
- 출력의 "검증 결과" 블록을 그대로 붙인다.
- 실패한 단계는 `build/verify/{단계}.log`에서 원인 줄을 찾아 함께 보여준다.
- 포맷 실패는 `./gradlew spotlessApply`로 고친다. 손으로 맞추지 않는다.

## 2. 기준선과 비교
- 이번 조각 전의 테스트 결과(전체·실패 수)와 비교한다. **원래 실패하던 테스트와 새로 실패한 테스트를 구분**한다.
  - 현재 알려진 실패: `BReadyApplicationTests.contextLoads` (`docs/TROUBLESHOOTING.md` T-002). 0단계에서 해결 예정.
- 새로 실패한 테스트가 있으면 이 조각은 끝나지 않았다.

## 3. 실제로 띄워서 관찰 (동작이 바뀐 조각)
테스트만으로는 부족한 변경(설정, 기동, API 계약, 트랜잭션·동시성)이면 직접 띄워 본다.
- 기동 로그에서 확인할 줄(포트, 프로필, 연결된 DB)을 짚는다.
- `curl`로 성공 1회·실패 1회. 요청과 응답 JSON을 그대로 붙인다.
- DB 상태가 바뀌는 변경은 조회 쿼리와 결과를 붙인다(쓰기 SQL은 실행하지 않는다).
- 관찰할 수 없었던 것은 "확인 못 함"과 이유를 적는다.

## 4. 정리
검증 결과는 이 형식으로 설계서의 "검증 증거"에 남긴다.
```
빌드: 포맷 통과 · 컴파일 통과 · 테스트 100개 중 실패 1 (기존 T-002, 신규 없음)
관찰: POST /api/v1/plans → 201 {"message":"success","data":{"planId":1,...}}
      POST /api/v1/plans (title 빈 값) → 400 {"errorCode":...}
```
